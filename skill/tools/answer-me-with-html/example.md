---
title: 订单状态由谁负责
subtitle: 把业务状态、页面反馈和人工选择分开，便于架构说明与交接
---

这份说明用于讨论订单页的状态归属，不是上线批准。服务端保存订单事实，页面负责展示；读者的意见需要人工带回现有项目流程。

## A 状态归属

| 内容 | 负责方 | 页面应如何处理 |
| --- | --- | --- |
| 订单是否已支付 | 订单服务 | 显示服务端返回的状态，不用动画完成事件推断支付成功 |
| 请求进行中 | 当前页面 | 显示忙碌提示，阻止同一按钮重复提交 |
| 请求失败 | 当前页面 | 保留订单内容，给出可操作的重试提示 |
| 是否采用此方案 | 项目负责人 | 阅读说明后明确回复；页面默认选项不代表同意 |

## B 一次确认请求

```flow TD
(读者点击确认) -> 页面检查: 当前是否已有请求
页面检查 -> 订单服务: 提交确认请求
订单服务 -> 页面展示: 返回真实订单状态
页面展示 -> (读者看到结果): 成功状态或失败提示
```

图中的箭头表示消息方向。页面收到明确响应后才更新业务状态；网络中断时不把等待结束当成支付成功。

## C 实现边界

下面是说明用的简短代码，不读取任何项目文件，也不执行代码。

```js title="订单页状态示意"
function describeOrder(order, pending) {
  if (pending) return "正在确认，请稍候";
  if (order.status === "paid") return "已支付";
  return "待支付";
}
```

交接时请附上项目实际接口、失败情况和测试证据。此处只表达状态归属，不声明组件符合性或视觉验收。

## D 需要读者回复的问题

```ask
先把哪一部分作为交接重点？
* 状态归属 | 先确认服务端事实与页面反馈的边界
- 失败恢复 | 先补充超时、重试与错误提示的具体行为
```

建议项只是起点。没有操作的问题仍然是未作答；请用面板评论说明理由，再打开回复摘要，把完整文字人工复制回对话。
