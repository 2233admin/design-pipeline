# Tunables

Tunables are the values an owner may change in a film or a page without editing code: a beat's
duration, an accent colour, a corner radius, a headline. They live in `tunables.json`; the project
reads them through a generated `tunables.js`. The same two files work for HTML with GSAP, CSS
animations, canvas, Three.js, Lottie, Anime.js and plain pages, because the runtime only reads data.

Files:

- `tunables.json`: `params` (what may change) and `values` (what the owner changed; a value equal
  to its default is not stored). Schema: `references/tunables.schema.json`.
- `tunables.js`: generated by `tunables sync`; never edit it. It defines `window.tunable(id)`,
  `--tn-<id>` custom properties on `<html>`, `data-tn-<id>` attributes for `select` and `checkbox`
  params, and fills every `data-tn-text="<id>"` element. It reads no clock, no random source, no
  storage and no location, so a render is repeatable.

## Declare

`film scaffold` (default template) already writes both files and the include line. For an existing
film or page:

```
designer-pipeline tunables init --project-root <dir>
```

and add the printed line as the first script of `<head>`:

```html
<script src="tunables.js"></script>
```

A param is a Playground control (`range`, `select`, `checkbox`, `color`, `text`) with an `id`
(lower-case letters, digits, hyphens), a `label` and a `group` for the owner, plus three optional
keys: `unit` (`px`, `s`, `deg`…; a CSS unit is added to the custom property), `window`
(`{"startSec": 3, "endSec": 4}`: where on the timeline the param is visible, so the probe samples
there and the panel seeks there) and `dynamic` (the project builds the id at run time, so `check`
does not report it unread).

## Read

Read a param at the one place that builds the thing it changes. Never copy the number into a
second place.

| Runtime | Read |
|---|---|
| GSAP, Anime.js, Motion | `tl.to(el, { x: 400, duration: tunable("beat-duration") })` before the timeline is registered |
| CSS | `background: var(--tn-accent)`; `border-radius: var(--tn-card-radius)`; `[data-tn-density="compact"] .card { … }` |
| Canvas, Three.js, WebGL | `ctx.fillStyle = tunable("canvas-fill")`, `material.color.set(tunable("accent"))` while building the scene |
| Lottie and other data-driven players | pass `tunable(id)` where the player takes its options |
| Copy | `<h1 data-tn-text="title-text">Hello</h1>` |

A timeline is built once at load, so a changed duration or ease needs the page to load again; the
panel and the probe do that for you. Do not read `tunable()` from a frame callback to animate with
it: that makes the value a clock.

## What to expose

Expose what an owner decides by looking: duration and delay of a beat, accent and background
colours, radius, spacing density, a headline, a switch for grain or a vignette. Give each a range
the design survives (`min`, `max`), a default that is the shipped look, and a label an owner would
say. Do not expose structure (layout grids, the order of beats), engine settings (fps, resolution),
or a value that only makes sense together with another one; declare the pair as a `select` of
named looks instead. Keep the list short enough that an owner can scan it.

## Check, preview, probe

| Command | What it answers |
|---|---|
| `tunables list` | params with defaults and current values |
| `tunables check` | `tunables.json` is sound, `tunables.js` is current and first in `index.html`, every param is read, every `tunable()` id is declared; each finding carries a `fix`; exit 2 on errors |
| `tunables set --param <id>=<value>` / `reset` | change values; a bad value exits 1 and no file changes |
| `tunables sync` | rewrite `tunables.js` after a hand edit of `tunables.json` |
| `tunables probe` | loads the page with each param at its value and at a changed one; warns `param-no-visible-effect` when no sampled frame differs; warns `probe-unstable` when the page changes by itself between two loads; project files are not written |
| `tunables panel` | local editor on 127.0.0.1 (one control per param, live preview, Save) |

`film check` adds a `tunables` step for a project with `tunables.json` and fails the render step
with `render-older-than-values` when the video is older than the values; render again with the
`fix` command and rerun the check.

## Panel

`tunables panel --project-root <dir>` prints a URL with a one-time token. Edits show in the
preview as a draft held in memory; only **Save** writes `tunables.json` and `tunables.js`, through
the same validation as `tunables set`. If the file changed after the panel loaded it, Save is
refused and the panel offers to keep your edits or use the file's values. The panel stops after 30
idle minutes (`--idle-minutes`).

The preview rewrites root-relative references in HTML attributes and CSS (`src="/tunables.js"`,
`url(/img/a.png)`) so they resolve inside the preview. A path built in a script, such as
`fetch("/data.json")`, is not rewritten: use a relative path there.

The panel previews; it does not render, and it has no accept or reject control. A saved change
needs a new render before it shows in the video, and the owner's acceptance of the result is
recorded in the owner's own words, as for any other change.
