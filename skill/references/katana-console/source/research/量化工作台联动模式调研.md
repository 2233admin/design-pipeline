# 借现成联动范式搭建 KATANAview 工作区骨架

**结论先行：** 成熟产品的"工作区联动"没有魔法，它收敛成四个可直接照抄的部件——(1) 一个**类型化的共享上下文对象**（FDC3 `fdc3.instrument` 式的 `type + name + id map`，各终端实际只传"一个证券标识"，图表额外传周期，账户从不进通道）；(2) **8 色编号通道 + 面板标题栏选择器**（FDC3 2.0 起的 SHOULD，Bloomberg Launchpad Group / Eikon Link Channel / thinkorswim 回形针 / NinjaTrader 色块 / Quantower 标题染色是同一套约定的变体），辅以 Kibana 式"钉住"把面板从通道里摘出；(3) **对象即链接 = `上下文 ⊕ 动词`**：Bloomberg 的"加载证券后任意 mnemonic 都对它生效"、FDC3 的 `raiseIntent("ViewChart", context)`、Grafana / Kibana / Datadog 对 `{clickedValue, row, vars, timeRange}` 做 URL 模板，本质相同；(4) **URL 即视图状态、工作区只保存对象引用与通道成员关系**（Grafana `var-x=`、Kibana `_g/_a`、OpenFin Page/Workspace 两级快照、LSEG Bookmark = app + instrument + parameters）。KATANAview 应直接采用 FDC3 的上下文词表与通道约定、OpenBB 的声明式 `paramName` 分组、Power BI 的"筛选 vs 高亮"逐对矩阵、Raycast 的两层命令面板，把 93 个面板"挂到"这条总线上，而不是逐对连线。真正需要自研的只有量化特有的部分：`Run / StrategyVersion / Account / Proposal` 这几种 FDC3 没有的上下文类型、"策略逻辑持仓 vs 账户真实持仓"的对账视图（vn.py 社区悬而未决的痛点）、"点持仓行 → 图表跳到对应周期并高亮成交"（没有任何被调研平台把它文档化）、以及把 Agent 提案当作一等上下文送进同一条通道。这些恰好对应用户提供的 Codex 四项目对比里 Object Registry → Workbench SDK → Run/Artifact → Approval/Audit 这条链——联动模型就是 Workbench SDK 的 `context schema`。

## 一、所有终端都把"联动"收敛成一个共享槽位：证券标识，而不是整个上下文

先纠正一个直觉：成熟终端的"面板跟随"并不是把整个状态同步过去。从 Bloomberg 到通达信，被传播的对象几乎只有**一个证券标识**。Bloomberg Launchpad 的 Group Manager 把组件编入 Group 1/2/…，"when a ticker code is changed in any one component, either through manual entry or simply drag/drop a security from a monitor into any component, all linked components will react" ([Bloomberg Launchpad Getting Started](https://my.lerner.udel.edu/wp-content/uploads/BB-Getting-Started-in-Launchpad.pdf))；Eikon 的 App Studio API 更直白——`contextChange/onContextChange` "provides only instrument data—custom payloads cannot be included" ([LSEG Developer Community 36452](https://community.developers.lseg.com/discussion/comment/36452))；FactSet 叫它 **Identifier Broadcast**，默认手势是双击标识符 "apply the identifier to all the company-specific displays in the tab" ([FactSet QuickStart Manual](https://www.ulethbridge.ca/sites/default/files/FactSetQuickStart_Manual%201%20of%202.pdf))；通达信在定制版面里对单元格右键"更改分组为'分组1'"后，点板块或股票，联动的分析图跟随，但每个窗口保留自己的周期 ([叩富网 Q&A](https://licai.cofool.com/ask/vipqa_7291791_42749905.html))。

零售/专业交易平台把这条规则精确到了属性级别：**非图表面板只同步 symbol，图表另有一条独立的 interval 链接**。NinjaTrader 8 的图表右上角有两个灰色方块，右边是 instrument link，左边是 interval link，Market Analyzer 和 SuperDOM 只有前者，因为 "their purposes are for scanning markets, placing orders, and managing trades" ([NinjaTrader 8 Help: Window Linking](https://static.ninjatrader.com/support/helpGuides/nt8/linking_windows.htm); [ninza.co](https://ninza.co/ninjatrader-8-linking-charts))。TradingView 的多图布局把可同步项列成五个独立开关——**Symbol、Crosshair、Interval、Time and Date Range、Drawing Objects**，且 Drawings "can only be synchronized on charts that contain the same symbol" ([TradingView Support](https://www.tradingview.com/support/solutions/43000629992-how-to-sync-the-charts-of-my-layout/))。Sierra Chart 是唯一把"链接"做成可扩展属性清单的：Symbol、Bar Period、Scroll Position、Session Times、Studies、Days to Load、Bar Spacing、Vertical Scale、Trade Window、Trade/Quote Symbol 各自一个复选框，加 Master Mode 决定谁驱动谁 ([Sierra Chart: Chart Settings](https://www.sierrachart.com/index.php?page=doc%2FChartSettings.html))。

**账户在所有被调研平台中都不进通道。** thinkorswim 把账户放在左上角全局菜单，含一个 "<TOTAL> SCHW (All Accounts)" 聚合视图 ([thinkorswim: Account Features](https://toslc.thinkorswim.com/center/howToTos/thinkManual/Getting-Started/Account-Features))；Quantower 的 Order Entry 面板有自己的 "Select Account" 按钮，而颜色链接文档只说同步 instrument ([Quantower: Order Entry](https://help.quantower.com/quantower/trading-panels/order-entry))。这意味着两个 SuperDOM 可以同色（同 symbol）不同账户。对必须多账户的 KATANAview 来说，这是一条可靠的先例：**账户是面板属性或工作区级范围，而不是跟随点击流动的东西**。

FDC3 把这些实践抽象成了可以直接抄的数据模型。每个 context 是一个 JSON：必填 `type`（路由用），可选 `name`，可选 `id` ——"a key-value map of equivalent identifiers across systems"，标准标识符大写（ISIN、FIGI、RIC、BBG），通用概念小写（ticker），自定义命名空间化（`com.company.foo`）([FDC3 Context Data spec 2.2](https://fdc3.finos.org/docs/context/spec))。复合类型通过**内嵌完整对象**而非引用组合：`fdc3.position` = `instrument` + `holding`，`fdc3.portfolio` = position 数组，`fdc3.chart` = `instruments[]` + `range`（TimeRange）+ `style` + `otherConfig: Context[]`（放指标等无标准格式的东西）([fdc3.position](https://fdc3.finos.org/docs/context/ref/Position); [fdc3.chart](https://fdc3.finos.org/docs/context/ref/Chart))。内嵌而非引用的好处是任何面板都能"剥"出它认识的那一层——收到 position 的图表面板取 `instrument` 即可。Bloomberg 的 Terminal Connect 还给了一个值得照抄的细节：`setGroupContext` 后 "Bloomberg will resolve any security you set and therefore its value may differ from what you sent" ([InteropIO finsemble-bloomberg](https://github.com/InteropIO/finsemble-bloomberg/blob/master/docs/README.md))——**广播前先归一化成规范对象**，别让 93 个面板各自解析 symbol 字符串。

观测类工具补上了终端缺失的另一半：**时间范围与键值过滤**。Grafana、Kibana、Datadog 都把"全局范围"做成顶部一行（时间选择器 + 变量下拉 / 过滤 pill）并镜像到 URL ([Grafana: Variables](https://grafana.com/docs/grafana/latest/dashboards/variables/); [Kibana: Routing, Navigation and URL](https://www.elastic.co/docs/extend/kibana/key-concepts/platform-architecture/routing-navigation-and-url); [Datadog: Template variables](https://docs.datadoghq.com/dashboards/template_variables/))。Datadog 的教训尤其适用于量化：范围能跨产品携带，只因为所有数据都带 `env/service/version` 这组统一标签，否则 "each product is scoped in isolation" ([Datadog: Unified service tagging](https://docs.datadoghq.com/getting_started/tagging/unified_service_tagging/))。KATANAview 的对应物是每条行情、成交、持仓、回测结果都带同一套 `instrument_id / strategy_id / account_id / run_id`——这是联动能否跨五个工作区成立的前提，与 UI 无关。

## 二、通道颜色、钉住与筛选/高亮：三套 UI 约定互补而非竞争

**通道的视觉约定已经是事实标准。** FDC3 2.0 以 SHOULD 推荐 8 个用户通道：`fdc3.channel.1` red、`.2` orange、`.3` yellow、`.4` green、`.5` cyan、`.6` blue、`.7` magenta、`.8` purple，"An app can only be joined to one User channel at a time" ([FDC3 API spec 2.2](https://fdc3.finos.org/docs/api/spec))。颜色集的来历值得知道：最初是 CSS 颜色名且含 brown，社区因对比度把它改成光谱顺序，并坚持 "Alphanumeric glyphs matched channel IDs explicitly serve colorblind users"，8 是为"future-proofing"选的上限 ([finos/FDC3 issue #717](https://github.com/finos/FDC3/issues/717))。Finsemble 用 "the channel selector menu on each window title bar"，io.Connect 用 "Channel Selector app shown in the header area"，并提供 Single / Multi Channel Mode 与**方向性通道（publish-only / subscribe-only）** ([Finsemble Interop docs](https://finsemble.interop.io/docs/connect-apps/interop/); [io.Connect Channels](https://docs.interop.io/desktop/capabilities/data-sharing/channels/overview/index.html))。FDC3 Sail 把 "User channels function as individual HTML tabs within the main browser tab"——**通道即工作区 tab** ([finos/FDC3-Sail](https://github.com/finos/FDC3-Sail))，与 FactSet "双击广播到本 tab 内所有 company-specific displays" 的默认作用域一致。

交易平台把这套约定做成了两个最有价值的**反馈细节**：thinkorswim 的回形针下拉 "shows the symbol currently linked to each color, allowing you to quickly identify existing links" ([thinkorswim: Interactive Elements](https://toslc.thinkorswim.com/center/howToTos/thinkManual/Getting-Started/Interactive-Elements))；Quantower "the panel's title will be colored to the respective color" ([Quantower: Link panels](https://help.quantower.com/quantower/general-settings/link-panels))。FactSet 甚至为此做了 **ALT+I "Channel audit"** 快捷键 ([FactSet QuickStart Manual](https://www.ulethbridge.ca/sites/default/files/FactSetQuickStart_Manual%201%20of%202.pdf))——说明"我现在到底链到哪了"是用户真实会迷失的问题。两个逃生口也反复出现：NinjaTrader 的 **Link All** 让窗口 "receive transmission from windows with any link color"，TradingView 的 watchlist 双击 "changes the symbol on all charts of the layout regardless of the sync setting" ([NinjaTrader 8 Help](https://static.ninjatrader.com/support/helpGuides/nt8/linking_windows.htm); [TradingView Support](https://www.tradingview.com/support/solutions/43000473336-how-do-i-change-the-ticker-symbol-for-all-charts-of-layout-simultaneously/))。两者解决同一需求：用户想要**一个主源（watchlist / scanner）驱动很多消费者**，而不想逐个配置。

**多通道成员资格是标准与实现分叉的地方，建议守标准。** FDC3 issue #242 记录了双方论点：支持方举"两个 portfolio 视图在不同账户上下文、共享图表/新闻面板响应任一"的真实流程，且 Finsemble 发现终端用户确实在用；反对方指出多源到达时 "without timestamps on context objects" 无法判断来源、"current channel" 语义模糊，并援引 Bloomberg 与 Refinitiv 不支持多通道而 "has proven sufficient for extensive financial workflows"；结果是从 2.0 里程碑移除 ([finos/FDC3 issue #242](https://github.com/finos/FDC3/issues/242))。Eikon 的实际行为更是反面教材：加入多个 colour channel "returns success but does not work" ([LSEG Developer Community 55623](https://community.developers.lseg.com/discussion/comment/55623))。单人量化公司没有"两个 PM 并排"的场景，一面板一通道足够。

**"钉住"是把面板从通道中摘出的正统做法。** Kibana 的每个结构化过滤器 "can be disabled, inverted, or pinned across all apps"；2014 年的原始设计是：在总览看板发现异常、加了过滤与时间范围后，希望它们"travel around with you"到专门看板，于是钉住的过滤器进入全局态 `_g`，留在过滤栏但视觉上区别于临时过滤，保存时复制进 app 态 ([Elastic: Filtering](https://www.elastic.co/docs/explore-analyze/query-filter/filtering); [elastic/kibana#2349](https://github.com/elastic/kibana/issues/2349))。同一思想在 Obsidian 的 "linked backlinks tab"（固定在某一篇笔记、不随当前笔记变）与 Grafana Explore 的时间链接开关（"When linked, changing the time in one panel automatically updates the other"）里重复出现 ([Obsidian: Backlinks](https://obsidian.md/help/plugins/backlinks); [Grafana: Explore](https://grafana.com/docs/grafana/latest/explore/get-started-with-explore/))。Power BI 的 Sync slicers 还给出一个更细的拆分：**Sync 与 Visible 是两列**——"If you sync a slicer to a page but don't make it visible on that page, slicer selections made on other pages still filter the data on that page" ([Microsoft Learn: Slicers](https://learn.microsoft.com/en-us/power-bi/visuals/power-bi-visualization-slicers))，即范围控件可以影响面板而不渲染在面板里。

**筛选还是高亮，必须逐对决定，并规定空选择的行为。** Power BI 定义得最干净：cross-filter "filters other visualizations to show only data that applies to your selection"，cross-highlight "highlights the related data in other visualizations without filtering them out"；默认两者同时生效，作者可对每个"源 → 目标"对改成 Filter / Highlight / None 并随报表保存；限制是 "You can only cross-filter line charts, scatter charts, and maps. You can't cross-highlight them" ([Microsoft Learn: Visual interactions](https://learn.microsoft.com/en-us/power-bi/create-reports/service-reports-visual-interactions))。Tableau 的 Filter action 有 Hover / Select / Menu 三种触发，并强制规定清除选择后 Keep filtered values / Show all values / Exclude all values 三选一 ([Tableau: Filter actions](https://help.tableau.com/current/pro/desktop/en-us/actions_filter.htm))。推论对量化很具体：持仓表选中一个 symbol 时，PnL 归因柱图应**高亮**（保留组合总量作基线），成交 blotter 应**筛选**（只看该 symbol），连续时间序列面板不能高亮只能筛选或叠加。

web 原生的两种联动实现是互补的参照。OpenBB Workspace 用**参数总线**：widget 用 `paramName` 声明参数，同名者可编入 group（apps.json 的 `groups[]` 含 `name/type/paramName/defaultValue/widgetIds`），表格列用 `renderFn: "cellOnClick"` + `actionType: "groupBy"` 让"点单元格 → 更新 group 参数"驱动其他 widget ([OpenBB: Apps.json Reference](https://docs.openbb.co/workspace/apps-json-reference); [OpenBB: Widgets.json Reference](https://docs.openbb.co/workspace/developers/json-specs/widgets-json-reference))。Deephaven 的 **Linker** 则是**面板直连**：从 Controls 菜单选源列、拖箭头到目标表的列、点 Done，之后**双击**源单元格把目标列过滤为该值；约束 "You can only link columns of the same data type"，"Links are dashboard-specific and persist when dashboards reopen"，表格高级设置可配 "inbound filters clear / override any previously applied filters" ([Deephaven: Controls](https://deephaven.io/enterprise/docs/interfaces/web/controls/); [Deephaven: Work with tables](https://deephaven.io/enterprise/docs/interfaces/web/working-with-tables/))。OpenBB 要开发者预先约定 paramName，用户零配置；Deephaven 让用户任意连线，但要手工拖。KATANAview 的 93 个面板是自己写的，走 OpenBB 的声明式路线成本最低；Deephaven 的"类型匹配才能连"与"入站过滤覆盖还是叠加"两条规则应当内置。Deephaven 的 **Filter Sets**（"capture the current state of all filters applied across the current dashboard"）与 MLflow 的 pinned runs 同解一个问题：探索时保持基准可见 ([Deephaven: Filters](https://deephaven.io/core/docs/how-to-guides/user-interface/filters/); [Databricks: MLflow experiments UI](https://www.databricks.com/blog/accelerate-your-model-development-new-mlflow-experiments-ui))。

## 三、对象即链接：Bloomberg 的"名词⊕动词"语法与 BI 工具的下钻模板殊途同归

Bloomberg 的交互语法是 `[security] <YELLOW KEY> <GO>` 加载名词，然后任何 `MNEMONIC <GO>` 都对它生效——"you can run any number of functions to analyze that security without having to reenter the security"；函数分 security-specific（DES "you must have the security loaded beforehand"）与 non-security-specific（WEI）；Autocomplete "makes the Bloomberg Terminal entirely discoverable from the command line" ([Duke: Bloomberg Getting Started](https://library.fuqua.duke.edu/docs/Bloomberg-Getting-Started-Guide-for-Students-English.pdf); [Imperial College: Bloomberg functions](https://library-guides.imperial.ac.uk/bloomberg/functions))。Terminal Connect 把一条命令拆成 **mnemonic + panel number (1–4) + securities[] + tail** ([InteropIO finsemble-bloomberg](https://github.com/InteropIO/finsemble-bloomberg/blob/master/docs/README.md))——这就是 `verb(context, target, args)` 的签名。"相关视图"在 Bloomberg 是 <MENU> 的 Related Functions 层级，在 Eikon 是每个对象工具栏的 **Related** 按钮，其内容 "may vary according to the instrument you are viewing and the object from which you are opening the related information" ([Eikon User Guide](https://cefr.uel.edu.vn/Resources/Docs/SubDomain/cefr/Eikon%20User%20Guide.pdf))——菜单同时依赖**对象类型**与**起点面板**。中文终端把它折叠成一个带 tab 的深度页：Wind 的 F9 深度资料含「速覽、公司資料、重要股東、交易數據、財務數據…同業比較」，同花顺 F10 / F7 个股全景，且「在不同页面所显示出来的右键菜单是不一样的」 ([Wind 使用手冊](https://home.lib.fju.edu.tw/TC/sites/default/files/2022-05/WFT_userguide.pdf); [长城证券同花顺版 help](https://www.cgws.com/fintech-oss-monthnews/cczqths_help.pdf))。

FDC3 把这套语法标准化为 **intent = 动词 + context 名词**：`fdc3.raiseIntent("ViewChart", {type: "fdc3.instrument", name: "IBM"})`，标准 View 类有 `ViewChart / ViewNews / ViewAnalysis / ViewOrders / ViewQuote / ViewInstrument / ViewHoldings / ViewResearch` 等；`raiseIntentForContext(context)` 让系统列出该对象可用的全部动词；`findIntentsByContext` 可只查询不执行 ([FDC3 Intents spec 2.2](https://fdc3.finos.org/docs/intents/spec); [FDC3 API spec 2.2](https://fdc3.finos.org/docs/api/spec))。广播与 intent 的分工在规范里很清楚：broadcast 是通道上的一对多状态同步，intent 是定向的请求/响应，可能启动目标并带回结果。Finsemble 的 resolver 对话框展示了成熟的 UX：悬停候选项时**高亮对应的已开窗口**、"Remember choice" 记住 (source app, intent, context type, destination) 四元组、为 `raiseIntentForContext` 提供动作下拉；被记住的选择 "persist in workspaces and clear when either source or destination app instances close" ([Finsemble Interop docs](https://finsemble.interop.io/docs/connect-apps/interop/))。规范另有一条对单页应用同样成立的时序规则：启动目标后代理需等待其调用 `addContextListener`，"handlers SHOULD be registered within 15 seconds"，并且 "When an app joins a User channel, or adds a context listener when already joined to a channel, it will automatically receive the current context for that channel" ([FDC3 API spec 2.2](https://fdc3.finos.org/docs/api/spec))——**懒加载的面板必须能在挂载后收到最新上下文的回放**。

BI 与观测工具则把"对象即链接"做成了**对上下文对象的 URL 模板**，而且四家的上下文对象惊人一致：`{clickedValue, rowFields, seriesLabels, globalVars, timeRange}`。Grafana data link 的 token 有 `__url_time_range`、`__field.labels.<LABEL>`、`__value.raw`、`__data.fields["Name"]`、`${var-myvar:queryparam}`，跨看板链接要显式带 `__url_time_range` 并勾 **Include all variables** ([Grafana: Configure data links](https://grafana.com/docs/grafana/latest/panels-visualizations/configure-data-links/))；Kibana drilldown 目的地保留 "the specific value selected by the user"、"active filters from the origin dashboard"、"the current time range" ([Elastic: Drilldowns](https://www.elastic.co/docs/explore-analyze/dashboards/drilldowns))；Datadog context link 用 `{{@attr.value}}`、`{{$var.value}}`、`{{timestamp_start}}` 并默认在每个 widget 菜单里给出到 host / traces / logs 的链接 ([Datadog: Context links](https://docs.datadoghq.com/dashboards/guide/context-links/))；Power BI drillthrough 目标页声明 Drillthrough filters 字段，右键任何匹配数据点即可跳转，系统 "automatically adds a back button"，且**不**自动带源页其他过滤——文档明说 "The drillthrough page only shows data for the selected item. Design your visuals to take advantage of this focused context" ([Microsoft Learn: Drillthrough](https://learn.microsoft.com/en-us/power-bi/create-reports/desktop-drillthrough))。Grafana 另有一个分层值得照抄：面板内手写的 data links 是局部的，而 **Correlations**（"how data in one data source is used to query data in another"）是管理员级、按数据源/字段注册的全局规则，渲染在 Explore 的日志条目与表格单元格里 ([Grafana: Correlations](https://grafana.com/docs/grafana/latest/administration/correlations/))。

四个文档化的**失效模式**对量化尤其致命。第一，Kibana："you cannot filter or drill down from a value created at query time"——Lens 公式、聚合结果没有字段映射 ([Elastic: Drilldowns](https://www.elastic.co/docs/explore-analyze/dashboards/drilldowns))；对应到量化：Sharpe、最大回撤这类派生指标不能作为下钻入口，除非它们回指到产生它们的 run / trades。第二，Datadog：日志与 trace 的关联依赖注入 `trace_id/span_id/env/service/version`，且 "Traces and logs are sampled independently" 导致目标可能为空 ([Datadog: Connect logs and traces](https://docs.datadoghq.com/tracing/other_telemetry/connect_logs_and_traces/))；对应：成交记录与行情 K 线如果不共享 `instrument_id + 时间戳精度`，"跳到成交处"就会落空。第三，Grafana 把 `Include all variables` 默认关掉，Kibana 默认带源过滤，Power BI 刻意不带——三种默认都站得住，但必须**明确选一个并告知用户**。第四，NinjaTrader 用户记录 "changing the instrument in an existing window ... lose[s] all alerts that are assigned to drawn objects" ([NinjaTrader forum 103450](https://forum.ninjatrader.com/forum/ninjatrader-8/platform-technical-support-aa/103450-linking-superdom-to-chart))——**上下文切换不得销毁 per-object 状态**（画线、告警、草稿订单必须按对象 key 保存）。

两个非金融工具提供了导航**层级**上的约定。VS Code 的三级升级——Ctrl+hover 预览、**Peek**（Alt+F12，"embeds the result inline"）、Go to Definition——其理由是 "We think there's nothing worse than a big context switch when all you want is to quickly check something" ([VS Code: Code Navigation](https://code.visualstudio.com/docs/editing/editingevolved))。Obsidian 的反链面板区分 **Linked mentions** 与 **Unlinked mentions**，带上下文片段，可内嵌在文档底部 ([Obsidian: Backlinks](https://obsidian.md/help/plugins/backlinks))；对量化，"某 symbol 的反链"就是交易它的策略、涉及它的订单与风控限额、提到它的研究笔记。Honeycomb BubbleUp 展示了"结果本身就是下一步菜单"：点任何一根柱子弹出 `GROUP BY field` / `WHERE field = value` 等动作，每个动作重跑查询并带永久链接 ([Honeycomb: Identify outliers](https://docs.honeycomb.io/investigate/analyze/identify-outliers))。

MLOps 工具则确立了量化缺失的那条链——**run 是一等对象**。MLflow 的注册模型版本 "linked to the MLflow run, logged model or notebook that produced it"，用可变 **alias**（如 `champion`）指向不可变版本 ([MLflow: Model Registry](https://mlflow.org/docs/latest/ml/model-registry/))；W&B 的 Lineage DAG 里 "Nodes with green icons represent runs. Nodes with blue icons represent artifacts"，同层 ≥5 节点自动聚簇并带搜索，版本页显示 "source version" 与 "producing run" ([W&B: Explore artifact graph](https://docs.coreweave.com/products/wandb/artifacts/explore-and-traverse-an-artifact-graph.md); [W&B: Link version](https://docs.coreweave.com/products/registry/link_version.md))。QuantConnect 是被调研平台里唯一把这条链画进实盘图的：live 结果页的 **Strategy Equity 图带 out-of-sample backtest overlay 与 deployment markers**，Code tab 保存部署所用代码快照，Live Dashboard "links all organizational algorithms back to their projects" ([QuantConnect: Live Results](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/results))。

## 四、URL 即视图状态，工作区保存对象引用而非像素

三家观测工具把范围值全部编进 URL：Grafana `var-<varname>=value`（可按变量 `skipUrlSync: true` 关闭）、Datadog `&tpl_var_<NAME>=<VALUE>`、Kibana rison 编码的 `_g`（"global UI state that should be shared and synced across multiple apps"：时间范围、刷新间隔、钉住的过滤）与 `_a`（"UI state scoped to current app"）；Kibana 用 `KbnUrlTracker` 持续改写导航链接以携带全局态，并坦承在客户端路由后 "there is no real need to follow `_g` and `_a` separation anymore"，但两层语义本身仍是最清晰的心智模型 ([Grafana: Variables](https://grafana.com/docs/grafana/latest/dashboards/variables/); [Datadog: Template variables](https://docs.datadoghq.com/dashboards/template_variables/); [Kibana: Routing, Navigation and URL](https://www.elastic.co/docs/extend/kibana/key-concepts/platform-architecture/routing-navigation-and-url))。Grafana Explore 对此的补充是：URL 随查询自动更新可直接分享，同时提供 `/goto/:uid` 短链 ([Grafana: Explore](https://grafana.com/docs/grafana/latest/explore/get-started-with-explore/))——长 URL 适合机器回放，短链适合人。Datadog 的 **Saved views** 则是"命名的范围快照"：保存查询、时间范围（相对范围保留、绝对范围固定）、可视化类型与 facet 子集 ([Datadog: Saved views](https://docs.datadoghq.com/logs/explorer/saved_views/))。

**工作区持久化在所有平台上都是两级结构。** OpenFin Workspace 分 Pages（一个 Browser 窗口内的 Views 与 Layouts，`savePage/getSavedPages`）与 Workspaces（多个窗口与页的集合，`saveWorkspace/getSavedWorkspaces`）([OpenFin Workspace Platform API](https://developer.openfin.co/workspace/docs/platform/latest/index.html))；io.Connect 的 Workspace Layout JSON 是 "the blueprint used by the Workspaces API to build the Workspace"，捕获结构（行/列/tab 组）、应用名、**每个应用的 context** 与配置 ([io.Connect Workspaces](https://docs.interop.io/desktop/capabilities/windows/workspaces/overview/index.html))；MetaTrader 5 分 Templates（单图：图表类型、指标、EA、分析对象）与 Profiles（"the entire workspace"）([MetaTrader 5 Help](https://www.metatrader5.com/en/terminal/help/charts_analysis/charts))；Quantower 是 panels → Groups（拖标题栏成嵌套 tab）→ Binds（Ctrl+~ 组成按比例缩放的超级面板）→ Workspaces（"Trading - Analysis - News" 式环境，XML 文件，每 5 分钟自动保存）([Quantower: Workspaces, Binds, Groups](https://help.quantower.in/getting-started/workspaces-binds-groups))。**存进去的不只是几何**：LSEG Workspace 的 Bookmark "save a page with its active instrument and parameters" ([LSEG Workspace Quick Start](https://thesource.lseg.com/TheSource/getfile/download/e3c972e1-0610-499f-a292-15c8739db94c))；TradingView 的 layout 保存 symbol、interval、指标、画线与交易按钮设置 ([TradingView: layouts quick guide](https://www.tradingview.com/support/solutions/43000746975-tradingview-layouts-a-quick-guide/))；Finsemble 把 intent resolver 里"记住的选择"也存进 workspace ([Finsemble Interop docs](https://finsemble.interop.io/docs/connect-apps/interop/))；OpenBB 的 apps.json 顶层就有 `tabs`（含每个 widget 的 `x/y/w/h` 与 `state.params`）、`groups`、`prompts` ([OpenBB: Apps.json Reference](https://docs.openbb.co/workspace/apps-json-reference))；FINOS Perspective 把每个视图的全部分析状态（group_by / split_by / filter / sort / expressions / plugin）做成可 `save()/restore()` 的 JSON ([finos/perspective](https://github.com/finos/perspective))。这与用户提供的 Codex 对比中 OpenTerminalUI 的 **Workspace Context**（保存的不只是 Layout，还有 ticker、interval、indicator、selected portfolio、filters）和 P1 建议"Saved Workspace 保存对象引用而非 UI JSON"完全一致（用户提供的 Codex 对比，codex_four_terminals.md）。

**已知的坑**集中在性能与一致性。Grafana 文档警告 `All` 选项 "can become very long and can have performance problems"，"Refresh: On dashboard load … slows down dashboard loading"，并建议常改的变量放最前 ([Grafana: Add template variables](https://grafana.com/docs/grafana/latest/dashboards/variables/add-template-variables/))——全局范围每变一次就触发所有面板重查，是通道模型的固有成本。QuantConnect 警告多开浏览器 tab 会让 "code sessions" "fall out of sync" ([QuantConnect: IDE](https://www.quantconnect.com/docs/v2/cloud-platform/projects/ide))——如果 KATANAview 允许多窗口，通道状态必须有单一权威源（BroadcastChannel / 后端）而非每个 tab 各存一份。Hex 的处理方式是对自动重算的最佳补充：Auto 模式"updating downstream and stale cells on each run"，另有 Cell only 等手动模式，过期单元 "marked with orange squiggles"，理由是消除 Jupyter "shared mutable state" 带来的不确定 ([Hex: Run modes and cell staleness](https://learn.hex.tech/docs/explore-data/projects/project-execution/run-modes-and-cell-staleness); [Hex: Beyond linear notebooks](https://hex.tech/blog/beyond-linear-notebooks/))。回测类面板不能在每次切 symbol 时自动重跑，必须显示"已过期"而非静默刷新。

## 五、量化工作台特有的缺口：run、账户与策略持仓没有被同一套联动串起来

对国内外量化平台的调研给出一个反向结论：它们在"联动"上普遍弱于金融终端与 BI 工具，但它们暴露的痛点恰好指出 KATANAview 的上下文对象必须比 `fdc3.instrument` 多出哪几个槽位。vn.py 官方文档承认"策略维护逻辑持仓… 实盘系统维护账户实际持仓，二者可能不一致"，移仓助手对合约"所有仓位"平仓且不区分策略来源；社区用户为此提议给每个运行策略建"策略账户"，得到的回复是"这个功能真的没有普遍的需求性"，提案至 2024 年未被采纳 ([vn.py CtaStrategy 文档](https://www.vnpy.com/docs/cn/community/app/cta_strategy.html); [VeighNa 社区帖](https://www.vnpy.com/forum/topic/4470-vnpyde-ying-gai-wei-mei-ge-yun-xing-ce-lue-chuang-jian-yi-ge-ce-lue-zhang-hu))。QMT 的"模型交易"把策略绑到一个账号与周期再选"运行模式"模拟/实盘，掘金是"交易"按钮选仿真账户后"自动跳转至 量化交易 板块" ([QMT 新人上手教程](https://dict.thinktrader.net/freshman/rookie.html); [掘金文档：投研](https://www.myquant.cn/docs2/quickStart/%E6%8A%95%E7%A0%94.html))——四家都是"同代码换引擎/换账户"，**没有一家在 UI 中保留"这个实盘实例来自哪次回测/哪组参数"的回链**；vn.py 的 CtaBacktester 参数优化结果与 CtaStrategy 之间甚至没有自动传递机制 ([vn.py CtaBacktester 文档](https://www.vnpy.com/docs/cn/community/app/cta_backtester.html))。行业评测把 "Backtest-to-live parity" 列为 "the #1 demanded feature across the board" ([autotradelab](https://autotradelab.com/blog/nautilus-vs-vectorbt-vs-freqtrade-20-python-quant-trading-frameworks-compared))。

多账户在这些平台里都是**按实例切换**而非**合并视图**：FreqUI "If multiple bots are connected, the dashboard will show an overview of all connected bots, allowing you to easily switch between them"；Hummingbot Dashboard 有 Instances 页，但已 "no longer actively maintained" ([Freqtrade: FreqUI](https://www.freqtrade.io/en/stable/freq-ui/); [Hummingbot: Dashboard](https://hummingbot.org/dashboard/))；QuantConnect 的多算法要求券商子账户，每个算法独占一个 node ([QuantConnect: Live Deployment](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/deployment))。Nautilus 则根本没有官方 GUI，维护者把 Web 前端定位为 "a future licensed add-on"，用户用 Jupyter、ClickHouse + Grafana 或社区 bt-visualizer 拼凑 ([nautilus_trader Discussion #245](https://github.com/nautechsystems/nautilus_trader/discussions/245))。两个被弃用的自建 dashboard（Hummingbot Dashboard、Kedro-Viz 原生实验跟踪迁往 kedro-mlflow ([Kedro-Viz Docs](https://docs.kedro.org/projects/kedro-viz/en/stable/))）给出同一警示：**堆页面的 dashboard 活不长，活下来的是把联动与回溯做进底层模型的（OpenBB group、Deephaven Linker、W&B lineage）**。

这些缺口与用户提供的 Codex 对比完全对得上：四个开源终端 "都没有打通 `Strategy Version → Experiment → Immutable Run → Artifact/Evidence → Deployment → Execution → Monitoring → Agent/Human Approval → Audit` 这条链"，建议以 `Object{id,type,version,status,owner,refs}` 的 Object Registry 为底、Run(mode=backtest/replay/paper/live) 统一、Approval Center 走 Proposal → Review → Approve/Reject → Execute（用户提供的 Codex 对比，codex_four_terminals.md）。本次调研补上的是：这条链在**前端**如何被点击、跟随与持久化——答案就是把 Run、StrategyVersion、Account、Proposal 做成与 `fdc3.instrument` 同等地位的上下文类型，走同一条通道、同一套 intent、同一个 URL 编码。Agent 侧也有先例：interop.io 在 OSFF 2025 NYC 的议题 "FDC3 and AI: Using FDC3 Intents as MCP Tools" 把 intent 当作 agent 的工具调用 ([interop.io community](https://community.interop.io/t/fdc3-and-ai-using-fdc3-intents-as-mcp-tools-osff-2025-nyc-session-recording/397))，FDC3 3.0 正在加入必填的 `traceId` 与 `clearContext()` ([FDC3 CHANGELOG](https://github.com/finos/FDC3/blob/main/CHANGELOG.md))——Agent 提案带 traceId 走同一条总线、人工批准即 `raiseIntent("Approve", proposal)`，是顺理成章的延伸。

## 六、KATANAview 设计结论（可执行）

以下每条标注来源：**[借：产品/标准]** 表示直接沿用，**[自研]** 表示没有现成先例、必须自己定义。实现形态：在单页应用内进程实现一个 DesktopAgent 风格的总线（通道、监听、最新上下文回放、intent 分发），**不**引入 FDC3 的 Web Connection Protocol / App Directory / PrivateChannel——那些是容器平台的问题；只借它的上下文词表、通道约定与 intent 语法 ([FDC3 WCP 2.2](https://fdc3.finos.org/docs/api/specs/webConnectionProtocol))。

### 6.1 上下文对象：一个通道携带多个类型化槽位，而非一个大对象

通道状态 = `Map<contextType, latestContext>`，每种类型独立保存最新值并在面板加入/挂载时回放 [借：FDC3 "current context replay on join"]。槽位如下：

| 槽位 `type` | 字段 | 是否随通道流动 | 谁产生 | 来源 |
|---|---|---|---|---|
| `fdc3.instrument` | `id: {ticker, exchange, FIGI?, ISIN?, katana.id}`, `name`, `market`, `assetClass` | 是（主槽位） | 盯盘表、持仓行、成交行、搜索 | [借：FDC3 context + id map；Bloomberg 归一化后广播] |
| `fdc3.timeRange` | `startTime/endTime` ISO 8601 或相对表达 `now-30d` | 是，但**可钉住** | 时间选择器、图表 brush、run 的区间 | [借：Kibana `_g` 时间 + 钉住；Grafana `__url_time_range`] |
| `katana.interval` | `"1m" / "1h" / "d"` | **独立链接**，仅图表类面板消费 | 图表 | [借：NinjaTrader 8 interval link 与 instrument link 分开；TradingView Interval 开关] |
| `katana.account` | `id`, `broker`, `engine`（Nautilus/vn.py/QMT）, `mode`（paper/live） | **否**。面板属性或工作区级范围，默认 `all` | 面板账户下拉、工作区设置 | [借：thinkorswim 全局账户菜单 + All Accounts；Quantower 每面板 Select Account] |
| `katana.strategyVersion` | `strategyId`, `version`, `name`, `refs` | 是 | 策略列表、run 详情 | [自研；对应 Codex `StrategyVersion`] |
| `katana.run` | `id`, `mode`（backtest/replay/paper/live）, `strategyVersion`（内嵌）, `timeRange`（内嵌）, `instruments[]`（内嵌）, `status` | 是 | 回测历史、实盘实例卡、调度任务 | [自研；形态借 MLflow run / W&B artifact 节点；内嵌规则借 FDC3 复合类型] |
| `katana.position` / `fdc3.position` | `instrument`（内嵌）, `holding`, `account`, `strategyInstance?` | 是（面板剥出 `instrument`） | 持仓表 | [借：FDC3 position；**`strategyInstance` 字段自研**，直指 vn.py 痛点] |
| `katana.proposal` | `id`, `actor`（agent/human）, `action`, `object`（内嵌任一上述类型）, `evidence[]`（Artifact refs）, `traceId`, `status` | 是 | 决策队列、Agent | [自研；对应 Codex Approval/Agent Trace；`traceId` 借 FDC3 3.0] |
| `katana.selection` | `objects[]`（多选）, `mode: "filter" / "highlight"` | 是 | 任意表格多选、图表框选 | [借：Power BI 筛选/高亮；Honeycomb 框选→BubbleUp] |

规则：复合对象**内嵌**而非引用下级对象（`run` 内嵌 `strategyVersion` 与 `instruments[]`），面板只取自己声明消费的那一层 [借：FDC3]。所有 id 走 `id` map，`katana.id` 是 Object Registry 的主键，`ticker/exchange/FIGI` 是别名 [借：FDC3 id 命名约定]。广播前由一个 resolver 归一化（`"IF2312"` → `{ticker:"IF2312", exchange:"CFFEX", katana.id:...}`），面板永远收到规范对象 [借：Bloomberg `setGroupContext` 的服务端解析]。

### 6.2 联动通道的 UI 约定

| 约定 | 具体做法 | 来源 |
|---|---|---|
| 通道数与颜色 | 8 条，`katana.channel.1–8`，红橙黄绿青蓝品紫，**每条带数字字形**；一面板只能在一条通道 | [借：FDC3 2.2 SHOULD + issue #717 色盲字形；不采用 Finsemble/io.Connect 多通道] |
| 选择器位置 | 面板标题栏左侧一枚色块/回形针；点开为 8 色列表，**每色旁显示它当前的 instrument 与 timeRange** | [借：Finsemble/io.Connect 标题栏选择器；thinkorswim 下拉显示每色当前 symbol] |
| 成员可视化 | 面板边框/标题染通道色；工作区级 **Channel audit** 浮层（快捷键）列出每条通道的成员与当前上下文 | [借：Quantower 标题染色；FactSet ALT+I Channel audit] |
| 默认作用域 | 新面板默认加入所在工作区 tab 的默认通道（通道 1）；通道可跨 tab | [借：FactSet tab 内默认广播；Sail 通道即 tab；Bloomberg Group 跨多屏] |
| 方向性 | 每面板声明 `produces[]` / `consumes[]`；盯盘表默认 publish-only，图表默认 subscribe-only，可在选择器里改 | [借：io.Connect 方向性通道；OpenBB `paramName` 声明] |
| 逃生口 | "Link All" 模式：面板接收所有通道；盯盘表**双击**行 = 无视通道设置广播到全部 | [借：NinjaTrader Link All；TradingView watchlist 双击；Deephaven 双击触发] |
| 钉住 | 面板级 pin 图标冻结该面板的某个槽位（如时间范围），其余槽位继续跟随；钉住的槽位在面板头部以不同样式显示 | [借：Kibana pinned filters 的"同栏不同样式"；Obsidian linked backlinks tab；Grafana Explore time-link toggle] |
| 筛选 vs 高亮 | 面板声明 `onSelection: "filter" / "highlight" / "none"`；离散标记类面板（表格、柱图）默认 highlight，明细类（blotter、日志）默认 filter，连续时序面板只允许 filter 或 overlay；**空选择行为**固定为 Show all values | [借：Power BI 逐对三态 + 线图不可高亮；Tableau 清除选择三选一] |
| 入站覆盖 | 通道入站的 instrument 默认**覆盖**面板本地过滤，面板可声明 `inbound: "merge"` | [借：Deephaven "inbound filters clear / override"] |
| 懒加载回放 | 面板挂载后注册监听，总线立即回放该通道每种类型的最新值；未注册前的广播排队 | [借：FDC3 15 秒握手 + join 时回放] |
| 过期提示 | 消费 `run` 或重计算成本高的面板不自动重跑，收到新上下文后显示"已过期"徽标并提供"重新计算" | [借：Hex 橙色波浪线 + Auto/手动模式] |
| 不销毁对象状态 | 画线、告警、草稿订单按 `instrument.katana.id` 存储，切换上下文只是切换可见集合 | [借：NinjaTrader 告警丢失的反面教训；TradingView drawings 仅同 symbol 同步] |

### 6.3 对象即链接的导航规则

每个可见的对象（symbol、持仓行、成交、run、策略版本、提案、调度任务）都是入口，统一语法 `verb(context, target?, args?)` [借：Bloomberg mnemonic + panel + securities + tail；FDC3 raiseIntent]。

| 规则 | 做法 | 来源 |
|---|---|---|
| 单击 | 把对象广播到本面板所在通道（更新对应槽位）。不导航 | [借：所有终端的 symbol 链接；OpenBB cellOnClick→groupBy] |
| 悬停 | 延迟弹出对象卡片（名称、关键字段、反链计数），不触发任何联动 | [借：VS Code Ctrl+hover 预览；OpenBB hover cards] |
| 右键 / 动作键 | 弹出该对象类型的 **Action Panel**，由 intent 注册表按 `contextType` 生成，首项为默认动作（Enter），每项旁显示快捷键 | [借：Raycast Action Panel；Linear 菜单显示快捷键；Eikon Related 随对象类型变化；FDC3 raiseIntentForContext] |
| 标准动词 | 先实现 `ViewChart / ViewQuote / ViewOrders / ViewHoldings / ViewAnalysis / ViewResearch` 六个 FDC3 名词，加自研 `ViewRun / CompareRuns / Deploy / Approve / Reject / Reconcile / Schedule / Explain` | [借：FDC3 2.2 标准 intents；**自研动词**对应 Codex Approval/Run] |
| 目标解析 | 同类型面板已存在 → 复用并闪烁其边框；多个候选 → 轻量 "Open with…" 浮层，悬停候选高亮对应面板，提供 "Remember choice"，记忆存在**工作区**里 | [借：Finsemble resolver + remember；FDC3 `instanceId/findInstances`；3.0 `newInstance`] |
| 三级升级 | 悬停卡 → Peek（侧抽屉，不离开当前工作区）→ 全导航（切工作区，带返回按钮与历史栈） | [借：VS Code hover/peek/navigate；Power BI drillthrough back button；Eikon Quote Back/Forward] |
| 下钻携带 | 跨工作区导航时携带 `{clickedObject, rowFields, timeRange, channel}`；**默认携带时间范围与通道，不携带源面板的本地过滤**，并在目标顶部显示"来自 X 的焦点视图"条 | [借：Grafana `__url_time_range`；Power BI "focused context" 立场；Kibana 带 value+time] |
| 可下钻的前提 | 只有带 Object Registry id 的字段可点；派生指标（Sharpe、回撤）不可直接点，需映射到产生它们的 run/trades 才可 | [借：Kibana "value created at query time" 限制] |
| 反链 | 每个对象详情页底部有 Backlinks 区：Linked（外键：交易它的策略、涉及的订单、限额、提案）与 Unlinked（研究笔记文本提及） | [借：Obsidian linked/unlinked mentions] |
| 全局关联规则 | 除面板内链接外，维护一张"字段 X 在类型 A 中 → 打开视图 B"的注册表（如任何表格里的 `run_id` 列自动可点） | [借：Grafana Correlations vs data links 两层] |
| 持仓行 → 图表 | `ViewChart(position)`：图表切 instrument、**切到该 run/策略的运行周期**、滚动到最近成交并高亮成交标记；行情与成交必须共享 `instrument.katana.id` 与毫秒时间戳 | [**自研**：没有任何平台文档化此行为；Datadog 采样不一致的教训] |
| 回测 vs 实盘 | `ViewRun(liveRun)` 的净值图默认叠加其 `strategyVersion` 的 out-of-sample 回测曲线并标记部署点 | [借：QuantConnect Live Results overlay + deployment markers] |

### 6.4 URL 与工作区状态持久化

URL 两层编码 [借：Kibana `_g/_a`]：`?g=`（跨工作区全局态：通道 1 的 instrument、timeRange、account 范围、钉住项）与 `?a=`（当前工作区局部态：激活 tab、面板级过滤）。每个槽位独立参数 `g.instrument=CFFEX:IF2312&g.range=now-30d&g.account=all`，可读、可手改 [借：Grafana `var-x=`、Datadog `tpl_var_x=`]。高频变化的槽位（crosshair、滚动位置）标 `skipUrlSync` [借：Grafana]。提供 `/goto/<shortId>` 短链供分享 [借：Grafana Explore]。多窗口时通道状态走 BroadcastChannel 同步到单一权威源，避免 QuantConnect 式失步。

工作区文档两级 [借：OpenFin Page/Workspace；MT5 Template/Profile]：**Page**（一个 tab：面板树 + 每面板 `{panelType, channel, pinnedSlots, consumes/produces 覆盖, 本地视图配置 JSON}`）与 **Workspace**（命名的 Page 集合 + 通道初始上下文 + 记住的 intent 解析选择）。面板的"本地视图配置"是可 `save/restore` 的纯 JSON（列、排序、过滤、图表样式）[借：Perspective viewer config；OpenBB `state.params`]。**只保存对象引用**（`katana.id` + `version`）而非对象快照，恢复时按 FDC3 的"重新投递上下文"顺序：先建面板、等监听注册、再回放 [借：io.Connect 布局含 per-app context；Codex "Saved Workspace 保存对象引用而非 UI JSON"]。另提供 **Saved View**（命名的范围快照：通道上下文 + 钉住项，不含布局）[借：Datadog Saved views；Deephaven Filter Sets]。

### 6.5 命令面板

两层 [借：Raycast]：**Root Search**（`Ctrl+K` 或任意字母数字键呼出）同时索引 Object Registry 的对象、工作区/面板、命令与 FDC3 动词；支持拼音首字母与代码模糊匹配 [借：同花顺 键盘精灵 "按下任意一个数字、字母或符号" 弹出、拼音首字母匹配；Bloomberg Autocomplete]。**Action Panel**（在选中对象上再按 `Ctrl+K`）列出该对象的 intents，首项 Enter 执行，分组可模糊搜索、每项显示快捷键与可复制的 Deeplink [借：Raycast Deeplink 节；Linear 快捷键教学]。支持复合语法 `IF2312@chart`、`run:abc@compare` [借：FactSet `C@N`；Bloomberg `security + mnemonic`]。面板头部始终显示当前范围（"IF2312 · 近 30 天 · 账户 all"），让用户知道动作作用于谁 [借：Linear/Appleton 对可发现性的批评]。Agent 可调用同一套 intents——每个 intent 自带 JSON schema，即 Codex 的 Capability Registry [借：interop.io "FDC3 Intents as MCP Tools"]。

### 6.6 与 Codex 四项目对比的对接

| Codex 对象 / 层 | 本报告的联动对应物 |
|---|---|
| Object Registry `Object{id,type,version,status,owner,refs}` | 上下文槽位的 `type` 就是 Registry 的对象类型；`id` map 的 `katana.id` 就是 Registry 主键；`refs` 决定反链面板的 Linked mentions |
| Workbench SDK（inputs/actions/views/context schema） | 面板声明 `consumes[] / produces[] / onSelection / inbound`（= context schema），注册 intents（= actions），导出视图配置 JSON（= views）；这是 OpenBB widgets.json + FDC3 AppD `interop` 字段的合体 |
| Run Registry / Artifact Store | `katana.run` 上下文类型；`CompareRuns` intent；W&B 式 lineage 面板；alias（`champion`）指向不可变 run 的部署 |
| Approval Center / Agent Trace | `katana.proposal` 上下文类型走同一通道；`Approve/Reject` intents；每个 intent 调用写 `Actor + Action + Object + Evidence + traceId` 审计行 |
| Execution Gateway "UI 不持有交易真相" | 账户不进通道、持仓面板只消费事件流；`Reconcile` intent 把策略逻辑持仓与账户持仓并排 |
| Global Search + command palette（P1） | 6.5 的 Root Search 直接索引 Registry |
| Saved Workspace 保存对象引用（P1） | 6.4 的 Page/Workspace 文档 |

### 6.7 必须自研的清单

没有先例可抄、需要自己定义并测试的：(a) `katana.run / strategyVersion / proposal / account` 四种上下文类型的 schema 与内嵌规则；(b) "持仓行 → 图表切周期并高亮成交"的完整语义；(c) 策略逻辑持仓 vs 账户持仓的对账视图与 `strategyInstance` 归属字段；(d) Agent 提案作为上下文在通道上流动、批准即 intent、带 traceId 的审计——FDC3 3.0 尚未发布，只能借思路；(e) 单页应用内的进程内总线（通道 Map、队列直到监听注册、intent 注册表与 resolver）——FDC3 没有现成的"同源组件版"实现，Sail 与 fdc3-for-web 都面向 iframe 且 "not yet ready for production"；(f) 五个工作区各自的默认 `produces/consumes` 矩阵与筛选/高亮默认值，需要用自己的 93 个面板逐个决定。

### 6.8 开发路线

**阶段 0（骨架，先于任何面板改造）**：实现进程内总线（8 通道、`Map<type, latest>`、回放、队列）、`fdc3.instrument` + `fdc3.timeRange` + `katana.interval` 三个槽位、面板标题栏通道选择器与染色、Channel audit 浮层。用 `@finos/fdc3` 的类型与 JSON Schema 定义标准槽位，自研槽位用同样的 schema 风格。验收：盯盘工作区内任意表格单击行，所有同通道面板跟随；双击行无视通道全广播。

**阶段 1（声明式挂载）**：给 93 个面板各加一份 `consumes/produces/onSelection/inbound` 声明，分批接入；先接盯盘与组合，再接研究/调度/档案。实现 URL `g/a` 两层编码与 Page/Workspace 两级保存（对象引用）。验收：复制 URL 到新窗口得到同一视图；刷新后钉住项与通道成员关系不变。

**阶段 2（对象即链接）**：intent 注册表 + resolver + remember；六个 FDC3 View 动词；hover 卡 / Peek 抽屉 / 全导航三级；全局 Correlations 注册表让任何 `run_id / order_id / instrument` 列自动可点；Root Search + Action Panel。验收：从任何工作区的任何对象两步内到达其图表、订单、run。

**阶段 3（量化专有槽位）**：`katana.run / strategyVersion / position(strategyInstance) / account` 进通道；`ViewRun` 叠加回测曲线与部署点；`CompareRuns`；`Reconcile` 对账视图；过期徽标与手动重算。验收：从实盘持仓行回溯到产生它的 run 与参数，再回到回测曲线，全程不输入任何代码。

**阶段 4（Agent 与审批）**：`katana.proposal` 槽位、决策队列面板消费它、`Approve/Reject` intents、每次 intent 调用写审计行（含 traceId）、intents 以 JSON schema 暴露给 Agent。验收：Agent 提案点开即带着 instrument/run 上下文跳到证据面板，批准动作与人工手动操作走同一条审计。

## 结论

这次调研最重要的转变是：**"联动"不是 UI 功能，而是对象模型的前端投影**。金融终端用 40 年证明了"只传一个证券标识 + 一面板一通道"足够支撑高强度工作流；观测工具证明了"范围进 URL、全局/局部两层、用户决定钉什么"是可分享、可回放的；BI 工具证明了筛选与高亮必须逐对声明；MLOps 工具证明了 run 必须是一等对象才有回溯。这四条线索在 FDC3 的 `type + id map + 内嵌复合 + intent` 模型上交汇，而 FDC3 本身正在朝 traceId、clearContext、instance 定向演进——与一个有 Agent 提案与审批队列的量化工作台的需求同向。KATANAview 的差异化不在联动机制本身（那应当尽量平庸、尽量像别人），而在于把 `Run / StrategyVersion / Proposal` 这几个行业里从没进过通道的对象送上同一条总线。

对开发顺序的含义是明确的：先做总线与 instrument 槽位（阶段 0），再给 93 个面板写声明（阶段 1），而不是先为某两个面板手工连线——Hummingbot Dashboard 与 Kedro-Viz 实验跟踪的弃用说明"先堆页面再想联动"的路线会在页面数增长时崩掉。证据上要坦白两点：几乎所有"用户痛点"都来自厂商文档、GitHub issue 与论坛，没有找到任何独立可用性研究；Codex 对四个开源终端的源码级断言也未经上游仓库核验。这些不影响结论的方向，但影响默认值的选择（例如下钻是否默认携带源过滤），那些默认值应当在阶段 1 用自己的面板实测后再定。
