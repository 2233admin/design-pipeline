# Built-in film methods

Open this guide for an explicit product promo/demo, feature loop, logo sting or motion study.
It adapts two complete source trees to the existing film workflow. It is a supporting method
after [job routing](capability-routing.md), not a second dispatcher. Ordinary UI, CSS, interactive
component and page-motion work keeps its current route and artifacts; a video reference alone
does not turn that task into a film. A component task may borrow one timing primitive without
adopting a storyboard or soundtrack.

## Choose only what the task needs

| Task | Select | Why and boundary |
| --- | --- | --- |
| Product film with an existing brand and real interface | `product-film`, optionally `cinetic` | Discover the actual tokens, components, voice and approved claims; compose a product action. Cinetic adds concept/technique/timing methods where useful. |
| Feature loop for a muted landing placement | `cinetic`, plus `product-film` if UI/brand discovery is needed | Choose a product-specific device and finite loop; prove the seam and muted comprehension. Silent placement comes from the brief. |
| Short logo sting | `cinetic`, optionally product discovery | Reuse the supplied identity and one motivated mark action. Alpha/social variants are separate requested outputs. |
| One uncertain movement | `cinetic` with `film scaffold --template motion-study` | Establish poses, timing and spacing in a bounded study; it is not a finished promotional film. |
| Existing footage cut to music, PV/MAD | [film-edit.md](film-edit.md) | Borrow concept or sound critique when useful, but keep the existing edit project and renderer. The maintained preparation below requires a composition storyboard. |
| Ordinary UI/CSS or an accepted motion website | Existing component/CSS/runtime methods | Do not run `film methods` or add a film project. Use [animation-thinking.md](animation-thinking.md) for the motion question. |

## Project authority and method adaptations

User instructions, supplied references, existing DESIGN/MOTION foundations, accessibility,
language, brand and accepted engine govern. Preserve a supplied orange palette, serif wordmark,
static hold, gradient or other deliberate choice. Upstream bans and review heuristics are
contextual prompts; they never create a new style gate. Use specific product states and approved
claims instead of inventing metrics, promises, features, logos or endorsements.

Choose techniques for their causal role in the selected concept. The complete
[273-entry catalog](../vendor/cinetic/upstream/skills/cinetic/assets/library/techniques.json)
contains recipes, source timing, use/avoid conditions and evidence labels. `film methods` selects
explicit IDs and returns each complete entry; it does not run `pick.py` or select randomly.
Browse [the technique index](../vendor/cinetic/upstream/skills/cinetic/references/technique-library.md)
to find an ID. Its evidence ratings describe upstream observations, not our certification.
Map the chosen technique to a beat, explain how the product's own objects carry it and record
omissions/adaptations in that beat's `note` or `reference.md`. A recipe mentioning Remotion,
60fps, fixed frame lengths or mandatory effects is a source example. Convert frame lengths to
seconds before adapting to the chosen fps; do not silently change the delivery settings.

HTML video uses [HyperFrames](hyperframes.md) and the existing paused GSAP composition contract.
An existing accepted Remotion, Blender or other runtime follows the existing governed selection;
this method does not install it. One clock and one property owner remain required. Product Film's
kit has useful Remotion TS/TSX camera, cursor and spring examples, but no generic compiled library
we promise to run. Reuse existing choreography before translating an example.

Use existing intake decisions. Ask only for missing product facts, audience, claims or constraints
that affect the output. Upstream mandatory interview rounds, checkpoints, nine concepts, beat
quotas, versions and approval rules do not replace the current authorized workflow. Existing owner
acceptance still comes from the owner, and prior rejections remain binding.

## Map discovery and direction to existing artifacts

1. **Inspect the product.** Use `project inspect` and direct source reads for design/voice rules,
   token owners, logo/assets, feature screens and states, previous film work and reuse licenses.
   View the real surface where available. Record paths, actual values and observation limits in
   existing `reference.md`/design notes. Identify components whose CSS transitions, timers, async
   images or render loops would introduce another clock.
2. **Choose reuse for each screen component.** Record `import-as-is` when the existing component
   is seek-safe, `frame-twin` when time-dependent state must be derived from the composition clock,
   or `redraw` with a concrete mismatch and source reason. A twin retains the real tokens, copy,
   geometry and states; a renamed generic card is not reuse. Hashes prove input identity only.
   Fixed screenshots can be honest frame twins of observed states; they do not prove live export
   of arbitrary React components, and animated state changes still need authored proof.
3. **Choose the concept and story device.** Cinetic's product verb, viewer pain and formal-device
   lenses help when direction is unresolved. Test whether the actual product objects and behavior
   make the concept specific, and whether the value survives a summary. Use the accepted direction
   directly when one exists. Map idea/device/grammar to existing `benefit`, `proofAction`, `grammar`,
   `subject`, `productAction`, `transformation`, `carrier`, `note` and `reference` fields; do not add
   another treatment schema. The ownership/deletion/muted/poster tests are creative questions.
4. **Plan and build one representative passage.** Use existing `film scaffold`,
   [choreography registry](film-choreography/registry.json), `film blocks` and pose study. Real
   subject actions, camera and edit responsibility remain separate. Keep current storyboard.v1;
   preparation invokes its existing gate, then author the chosen motion and inspect the result.
5. **Plan beats and sound from one clock.** The adapter below computes frame/second positions,
   velocity peaks, spring contact/settle cues from the same curves used by the picture. Put the
   resulting seconds into existing `sound.cues`/`soundCues`; use `film score`,
   [film-score.md](film-score.md), [audio-gate.md](audio-gate.md) and existing
   [asset/audio tools](../tools/art-motion/assets-audio.md). A chosen grid is not a measurement of
   an unheard song. Audition music and check intended sync/counterpoint; audio analysis candidates
   are not instrument or listening evidence. A muted placement can intentionally remain silent.
6. **Render, critique and deliver.** Use the selected existing renderer and `film check`;
   inspect fixed and reordered seeks, actual action/handoff frames, text, product states, decoded
   colors, sound when present and loop seams. Report Component Conformance and Visual Acceptance
   separately. Correct the weakest passage before extending it. Keep media/provenance/render
   evidence in the existing workflow; changed source, storyboard or snapshot invalidates or reopens
   its dependent evidence. Preparation notes are neither a receipt nor creative acceptance.

## Maintained callable preparation

Start from an existing film project with its actual, gate-passing `storyboard.json`. For a new
project run `film scaffold`, replace the example beats and use the existing storyboard check.
Create a small task selection file; it is tool input, not a replacement storyboard or receipt:

```json
{
  "task": "product-film",
  "methods": ["product-film", "cinetic"],
  "concept": "The actual preferences panel records a change and shows its saved state.",
  "brand": [{ "file": "src/preferences.css", "note": "Inspected product tokens and states." }],
  "components": [{
    "file": "src/Preferences.tsx",
    "mode": "frame-twin",
    "reason": "Preserve actual copy and tokens; drive the submit transition from the film clock."
  }],
  "techniques": ["cam-isolating-push", "pd-ui-native-transitions"]
}
```

`task` is `product-film`, `feature-loop`, `logo-sting` or `motion-study`; `methods` selects
`cinetic` and/or `product-film`. Product Film requires real brand and component files with reuse
reasons. Cinetic requires at least one explicit technique ID. All provenance paths are relative
to CLI `--root`, which may be the product repository while `--project-root` is its film subfolder.
Files must exist inside that root, including after symlink resolution; URLs, fabricated paths and
directories are not file evidence. This does not automatically crawl or validate product claims.

```sh
designer-pipeline film methods --root <product-repo> --project-root films/promo --input films/promo/plan.json --json
designer-pipeline film methods --root <product-repo> --project-root films/promo --input films/promo/plan.json --write
```

The first command is read-only. The second writes `film-methods.md` with source revisions,
brand/component hashes, full chosen recipes and next steps. When Cinetic is selected it also writes
`lib/cinetic-motion-source.js` with original upstream bytes, its MIT `lib/cinetic-LICENSE`, and
`lib/film-motion.js`, our bounded frame-rate adapter. It leaves the existing storyboard, composition,
reference, sound and QA notes intact. Existing method files require `--replace`; all output paths
are contained and checked before writing. Source bytes must match their locked manifest hashes.

Load the two scripts in order in the actual composition:

```html
<script src="lib/cinetic-motion-source.js"></script>
<script src="lib/film-motion.js"></script>
```

```js
const M = FilmMotion.create({ fps: 30, bpm: 120 }); // chosen grid; no measured soundtrack claim
tl.to("#actual-subject", { x: 180, duration: M.sec(30), ease: M.E.ui }, M.at(1, 1));
const contact = M.settleOf(M.b(1, 1), M.b(1, 3), M.E.ui);
const cueSec = M.sec(contact); // use this same curve/event in the existing sound cue plan
```

The installed `lib/film-motion.js` also supports Node `require`. `create` exposes caller-fps
`b(bar, beat, sixteenth)`, `sec(frame)` and `at(...)`; source `E`, `SPR`, `springFn`, `peak`,
`settleOf`, `startFor`; and `spring(config, epsilon)` with an integer caller-frame duration and
exact ease endpoints. Springs/eases are pure functions and do not accumulate frame state.
Unusually slow springs that exceed the source's 20-second settle scan are rejected; use an
authored longer study rather than extending that source solver implicitly.
This adapter does not select a tempo, compose audio, own the render loop, add another GSAP instance
or apply source style bans. Other upstream motion exports remain readable source; they are not
advertised as configurable maintained APIs. Do not use the source's hardcoded 60fps grid alongside
the adapter grid in the same film.
