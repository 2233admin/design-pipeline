# Design

Follows `AGENTS.md` and `openspec/project.md`. Every decision below can be reversed; each has its reason. Words are plain on purpose (`skill/references/plain-language.md`). Five words are used in a fixed way. The **tool list** is the one checked list of what exists and where it is taught (`scripts/tool-list.json`); `next` and `--help` stay the source for what they say. The **tool map** is the readable page made from it (`skill/references/tool-map.md`). An **entry command** is a command that tells you what to do next; there are three: `next` (with `decide`), `route` (with `toolchain` and `execution`, which use its plan), and the OpenSpec change commands `status`, `plan`, `run` (with `change`); the brief called them routers. The **repo skill** is the file `.claude/skills/design-pipeline/SKILL.md`, which Claude Code reads when it works on this repository; `SKILL.md` alone is `skill/SKILL.md`, the first page of the shipped skill. The **dispatcher** is the code in `cli-core.cjs` that picks the handler for a command and, after T6, refuses an action that the table does not list. The change id `add-capability-registry` is the working name of the first draft.

## 3. Decisions

- **D1. One new JSON file, next to the script that reads it and not shipped; only the generated map ships.** `scripts/tool-list.json` sits beside `scripts/tool-list.cjs` and `scripts/test-manifest.json`, the other data file that only repository scripts read. It is not one more list in `skill/references/` next to `job-registry.json` and `companion-capabilities.json`: those are read by the running skill, and this one is read only by the script and the test. It is not an extension of an existing list either (fact 1). JSON is what the other lists use and what a test, a generator and, later, a stage module can read without a parser. Not shipping it has three reasons: it is about 84 KB (the map is about 25 KB) and `SKILL.md` tells agents to read only what the current step needs; no command reads it while it runs, so a copy in the package would have no reader; and it holds maintainer-only entries and reasons that a user of the package does not need. The package is built from `skill/` (`packageRoot`) and the paths in `required` are relative to it, so a file in `scripts/` cannot ship by accident. The map ships and is listed in `required`, because `SKILL.md` points at it. There is no `.schema.json`: the rules of section 4 are the contract, checked by the test (the repository has 71 schemas and none is loaded at run time).
- **D2. Entries describe a tool or a guide, and never decide anything.** An entry says what it is, who uses it, whether the author is shown it, its one official form, and where it is taught. It has no keywords, no priority and no rule that routes a request. That is why it is not a fourth entry command (section 8).
- **D3. Two fields, six allowed pairs.** `status` says whether an entry is alive (`active`, `alias`, `deferred`, `removal-candidate`). `exposure` says who is shown it (`public`, `expert`, `internal`). The six classes an earlier review asked for (it called them groups) are the six allowed pairs (section 4.2), so "six classes" is a rule the check enforces and not only words. The 18 headings of the map are called groups in the file; they are only headings.
- **D4. `internal` means maintainers, release, QA or plumbing, and always has a reason.** A tool an author could use but that no guide teaches stays `expert` and says `noGuide: true`; the map lists it under "No guide yet". Hiding it would give two answers to "what is offered": the help lists 141 of the 142 rows. Writing a guide, or hiding the row on purpose with a reason, is then a one-line data edit that a person decides.
- **D5. Stages are the workflow's own, written `deliverable:stage`, and only `public` entries have them.** A stage pair is a claim the tests can prove (section 6, checks c and d). For the many tools used on demand the honest value is "any stage", which is an empty list. Writing `deliverable:stage` and not a bare stage removes a real ambiguity: `decide` is named at `film:reference` and `web:reference` but never at `edit:reference`. No `phases` and no `tiers` field for now (section 8).
- **D6. The checks are one-way where the facts are one-way.** A `next` action that names a command makes that command `public` (checked both ways). A guide that names a command does not make it `public`; only `public` implies that a `next` action or a workflow guide names it. This keeps a wording change in a guide from failing QA. `SKILL.md` and the repo skill may name any `active` entry, including a maintainers-only one.
- **D7. The readable stage map is generated, by a repository script, not by a new command.** `node scripts/tool-list.cjs --write` writes `skill/references/tool-map.md`; `--check` and the test compare. The stage order comes from the workflow's own stage lists. No `designer-pipeline` command is added.
- **D8. The help text and the `next` texts stay hand-written and are checked.** Generating the help would need a model of every flag (`KNOWN_OPTIONS`), which is a second list to keep. Generating `next` would change texts that have deep-equality tests, for the gain of looking up one name. Both are listed as later steps with the evidence that would justify them (section 8).
- **D9. One small change to shipped code, in `skill/scripts/cli-core.cjs` only (T6); the rest reads what is already exported.** The command table already lists the actions of the 22 commands that route through it. T6 makes the 20 commands that run their own handler list theirs too: each gets its names in the table (`actions: [...]`, and `gates` for `verify`), and the ten commands that take no action say so (`actions: []`). The dispatcher refuses a name the table does not list before the handler runs, including a stray word after `next` or `decide` (the list of eight command names in `dispatch` is replaced by this table entry, with the same words), and `commandPaths()` exports the rows, always as a list. That makes the list exact by construction (every action the CLI accepts is one the table lists) and gives the tool list and the help something to be compared with (fact 15). Alternatives weighed. (a) Rewrite the 20 handlers as one function per action, so that the table's `run` entries are the real dispatch: not now; it touches about 700 lines in 20 functions, and a full list does not need it (the follow-up `split-command-handlers-by-action` of section 11). (b) Read the `action === "..."` names out of the handlers' text in the test: rejected, because it depends on the layout of the code, two handlers do not use that form, and it would prove what the text says and not what the CLI accepts. (c) Names beside the handler with no refusal (metadata only): rejected, because nothing would stop the handler from accepting an action that the list lacks, so a full list would again be a promise that the test cannot prove. (d) A private module that the runtime and the script both import: rejected, because the runtime needs no such data. What T6 proves and what it cannot is stated in section 11.
- **D10. The three entry commands are not merged now.** Section 8 lists the evidence that would change that.
- **D11. Guide entries are the 15 that `SKILL.md`, the repo skill or `next` name, not the 68 reference documents.** They are the 13 documents and the kit folder that `skill/SKILL.md`, the repo skill or a `next` action name, and the generated map itself (`SKILL.md` and the repo skill will name it, so it must be in the tool list). Other documents stay reachable through a row's `guide`. Nothing routes from the tool list, so leaving the other documents out hides them from no one.
- **D12. Wrapper scripts are recorded as `aliases` (other spellings), not as entries.** 21 scripts repeat a command in-process and 4 more are the form some guides teach. Ten of them have no reference at all and are candidates for a later removal; this change removes nothing.
- **D13. Every check is a function that returns problems, and the test drives each one with a broken input.** A check that only ever runs on the real repository could be broken and stay green. Each check takes its inputs as arguments (`collectInputs` builds them from the repository), so the test can change one input and expect the code (section 6).
- **D14. Every script that starts with `#!` is accounted for.** It is an entry's official script, a spelling in `aliases`, or a line of `internalScripts` with a reason. A new script cannot appear without someone saying what it is.
- **D15. The tool list comes before the web capability skills, and the rules are applied to today's rows.** Where the rules produced a surprise (two `removal-candidate` rows, ten `expert` rows with no guide) the appendix says so and asks the owner (section 12).

## 4. The tool list format

### 4.1 Top level and entry

```
{ "schema": "design-pipeline.tool-list.v1", "version": "1",
  "groups": [ ...18 map headings, in order... ],
  "internalScripts": [ { "script": "render-score.cjs", "reason": "..." }, ... ],
  "entries": [ ... ] }
```

| field | required | meaning |
| --- | --- | --- |
| `id` | yes | Command: words joined by `-` (`verify --gate x` is `verify-gate-x`). Script: `script-<file>` without `.cjs`. Guide: `doc-` and the path under `skill/` without a leading `references/`, without the ending `.md` or `/`, each other `/` turned into `-` (`references/workflow-film.md` is `doc-workflow-film`; `evals/web/README.md` is `doc-evals-web-README`). Must equal the value computed from `official`. |
| `official` | yes | An object with exactly one key: `command` (`"film check"`), `script` (`"init-website-clone.cjs"`, in `skill/scripts`) or `doc` (a path under `skill/`, such as `"references/workflow-film.md"` or `"evals/web/README.md"`, or a folder ending in `/`). |
| `kind` | yes | `creative-guide`, `generator`, `checker`, `evidence-capture`, `evaluation`, `maintainer-release`, `vendored-upstream` (copied from an outside project). |
| `audience` | yes | One or more of `author` (whoever builds the page or film), `reviewer` (a person who judges or approves), `maintainer`, `internal`. |
| `deliverables` | yes | Any of `film`, `edit`, `web`, `ui`. Empty only for `internal` entries. |
| `stages` | yes | Pairs `deliverable:stage`. Empty unless `exposure` is `public`. |
| `exposure` | yes | `public`, `expert`, `internal`. |
| `status` | yes | `active`, `alias`, `deferred`, `removal-candidate`. |
| `group` | yes | One of `groups`. Used by the map. |
| `summary` | `public`, `expert` | Plain words, at most 160 characters, shown in the map. |
| `guide` | command or script that is `public` or `expert`, unless `noGuide` | The one document under `skill/` to read for it: a path that exists, optionally followed by `#` and a heading anchor (`references/workflow-film.md#check` is the section `## check`; the anchor must match a heading of the file). It teaches the command or the job that uses it and may name the command only in prose. For `next` and `decide` it is `SKILL.md`. |
| `noGuide` | no | `true` only on an `expert` entry with no `guide`. |
| `reason` | not `active`, or `internal` | Why it is hidden or retired, in one sentence. |
| `aliasOf` | status `alias` | Id of an `active` entry that does the same thing. |
| `aliases` | no | Other spellings that run the same thing, such as `node skill/scripts/check-ui-ir.cjs`. |
| `includedIn` | no | Object `{ "film": "film-check" }`: the umbrella command that runs this same check as one of its steps for that deliverable, when the step has its inputs (`film check` runs the audio check only when the film has sound). Partial overlaps are not recorded: `film check` reads a frame's pixels but not its text boxes, and it re-runs the storyboard check without recording the gate that `next` waits for. |

A **guide path** in a text (`SKILL.md`, the repo skill, a `next` action) is a path under `references/` or `evals/`, written with or without a leading `skill/`, that ends in `.md`, or a folder path that ends in `/`. When a text names a path, trailing `.`, `,`, `;` and `)` are dropped first. A path elsewhere (`scripts/tool-list.json`, `docs/...`) is not a guide path. A **heading anchor** is what a Markdown viewer makes of a heading: the words in lower case, letters, digits, spaces and `-` kept, each space turned into `-` (`## Gate one` gives `gate-one`, `## check` gives `check`). A heading is a line that starts with one to six `#` and a space, outside a code fence.

### 4.2 The six allowed pairs

| status | exposure | class of the earlier review |
| --- | --- | --- |
| active | public | public workflow action |
| active | expert | expert or manual tool |
| active | internal | internal dependency |
| alias | internal | alias |
| deferred | internal | deferred stub |
| removal-candidate | internal | removal candidate |

Any other pair is rejected with `PAIR`. An alias, a deferred entry and a removal candidate are still callable and still listed by `--help`; "internal" says only that the author map leaves them out (its last section lists them by name). `public` means `SKILL.md`, the repo skill, a `next` action or a workflow guide sends the author there. `expert` means the entry works, has a guide (or `noGuide`), and is listed in the map without being a step. `internal` means maintainer, release, QA or plumbing work. A command that `job-registry.json` names is at least `expert`.

### 4.3 Groups

The 18 map headings, in this order: Start and decide; Film; Edit; Web pages; Shared checks; Review; UI and web; Guided brief and templates; Design synthesis; Design systems; Components; Reference, reconstruction and scenes; Website cloning; Knowledge catalogs; Tools and routing; Change lifecycle; Interchange checks; Maintainers.

### 4.4 Codes

Structure codes (`validateToolList`):

| code | fires when |
| --- | --- |
| `LIST_SHAPE` | the top level is not `schema`, `version`, `groups`, `internalScripts`, `entries`, or a group is repeated, empty, or unused |
| `ENTRY_KEYS` | an entry lacks a required key or has a key the table does not list |
| `ID_MISMATCH`, `ID_DUPLICATE` | the id differs from the value computed from `official`, or two entries share an id |
| `ENUM` | `kind`, `audience`, `deliverables`, `exposure`, `status` or `group` holds a value that is not listed |
| `PAIR` | the pair of `status` and `exposure` is not one of the six |
| `OFFICIAL_ONE`, `OFFICIAL_DUPLICATE` | `official` has zero or several keys, or two entries share a value; or an alias spelling equals another entry's `official` |

## 5. Where it lives and how it is read

- **Data.** `scripts/tool-list.json`, in the repository and not shipped (D1). **Generated view.** `skill/references/tool-map.md`, shipped and listed in `required` of `package-resources.json`.
- **Script.** `scripts/tool-list.cjs`, in the repository and not in the package. A problem is `{ code, id, message }`. It exports:
  - `loadToolList(file?)` and `collectInputs(repoRoot, list)`. The second reads the repository once and returns everything a check needs: the help text (`publicHelp()`), the job registry, the stage lists and the `next` actions (from the `stages` of each stage module for `film`, `edit` and `web`, and by running `next` for a deliverable that has no stage module, that is `ui`; every tier and mode, on an empty and a full project, plus the start action), the texts of `skill/SKILL.md`, the repo skill, the workflow guides and the files of check e, the headings of each file that an entry's `guide` points at, the scripts that start with `#!`, `required`, the map, the rows of the command table (`commandPaths()`) and the answers of the 84 handler rows that it drives in empty temp folders (section 6, check b).
  - `validateToolList(list, inputs)` (structure codes) and the five surface checks `checkCommands`, `checkNext`, `checkSkillFiles`, `checkLiterals`, `checkMap`, each `(list, inputs) -> Problem[]`; `runChecks` runs all of them.
  - Small helpers the test also uses: `helpPaths(helpText)`, `commandLiterals(text)` (every `designer-pipeline <first> [<second>]` of a text, unfiltered), `guidePaths(text)`, `headingAnchors(markdown)`, `renderMap(list, inputs)` and `walkStages(deliverable, tier, mode, api?)`, the `ui` walk (`api` defaults to the `workflow-core.cjs` exports, so a test can pass a stub that returns a stage the walk cannot finish).
- **Modes of the program.** `--check` runs `runChecks` and exits 0, or 1 with the problems; it never writes in the repository (it does run 84 rows through `execute` in empty temp folders, about a second; with `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` and `XDG_*` pointed at an empty folder in the trial, nothing was written there and `git status` did not change). `--write` renders the map, writes it, and only then runs the checks and exits as `--check` would. That order lets the first `--write` create the map file that the tool list itself lists.
- **One change to shipped code (T6, D9).** The script imports only what shipped modules export: `publicHelp`, `execute` and `commandPaths` (`cli-core.cjs`; the last is the one T6 adds); `DELIVERABLES`, `TIERS`, `initState`, `nextAction` and `decide` (`workflow-core.cjs`); and `stages` of each module in `skill/scripts/workflows/`. It finds a stage module by the name of the deliverable (`workflows/<deliverable>.cjs`, not `shared.cjs`); a deliverable with no such file is read by running `next`. The `ui` walk finishes a stage with `decide` (`intake`; `deliver` for `work`) and stops with a clear message if a stage cannot be finished that way, so a new `ui` stage cannot pass unseen.
- **No command reads the tool list.** Not the CLI, not `next`, not `doctor`. Only the script and the test read it, so a wrong entry cannot change how a command behaves.
- **Why the script and the list are not shipped.** No user runs the script, and no command reads the list; shipping code or data that nothing at run time uses is dead weight (D1).
- **Why the stage modules do not read it now.** A stage's action carries flags and prose, and `tests/workflow-next.test.cjs` compares them exactly. Reading the tool list would replace one word by a lookup and risk the texts. It is worth doing when a surface is generated (section 8).

## 6. The checks

One new file, `tests/tool-list.test.cjs`, listed in `scripts/test-manifest.json`, run by `node scripts/qa.cjs`. Each check names the row, file or stage that disagrees. For each check the test runs it once on the real inputs (no problem expected) and then on inputs changed in the one way its rule forbids (its code expected).

- **(a) Structure.** `validateToolList` on the real tool list gives no problem. A table of copies of the tool list with one mistake each gives the code of section 4.4 for each of the structure codes (two officials, repeated id, wrong id, unknown kind, empty group, unknown top-level key, alias of an alias, alias with no target, `alias` with `expert`, a `removal-candidate` with no reason, a shown row without summary, an `expert` command with neither guide nor `noGuide`, `noGuide` on a `public` row, an `expert` row with stages, a stage of a deliverable the entry does not serve, a shown entry with no group, a shown entry with no deliverables, a missing guide file, a `guide` heading that the file does not have, an unknown `includedIn` key, an `official` script that does not exist, a repeated official form, a script that starts with `#!` and is accounted for nowhere). A command that does not exist is not a structure mistake: it is found through the help (check b). A separate test asserts that `required` holds the map (`references/tool-map.md`); the tool list cannot be listed there, because it lies outside `skill/`.
- **(b) Commands, help and jobs (`checkCommands`).** `helpPaths(publicHelp())` equals the set of command entries whose status is not `deferred` (`HELP_ENTRY`, in both directions: a help line with no entry, an entry that is neither in the help nor `deferred`, a `deferred` entry that the help names). Every command of `job-registry.json` is an `active` entry with exposure `public` or `expert` (`JOB_TARGET`). Broken inputs: an extra help line, a help line removed, a `deferred` entry that the help names, a job that names an alias. Each `deferred` command entry, run through `execute`, answers `COMMAND_DEFERRED`. **The command table (T6).** `collectInputs` calls `commandPaths()`. The rows it gives (a command with no action is one row, a command with actions is one row per action, and `verify` one more per gate) must be exactly the command entries of the tool list, in both directions (`TABLE_ENTRY`). With `HELP_ENTRY` that makes the help, the list and the table agree row for row; `source add` is in the table and the list and not in the help. The test also runs each listed action of the 20 handler commands in an empty temp folder with `--root`, and requires that no answer carries `UNKNOWN_COMMAND` or `UNKNOWN_GATE` (`DEAD_ACTION`): 84 rows. `change`, `component-first-v2` and `verify --gate` get the one input they read before the action (an existing `--change-root` with `--expected-sha256`, or an `--artifact` file holding `{}`); without it a wrong name would hide behind `OPTION_REQUIRED` (fact 15). `designmd sync` is not run (it may use the network), and `component-first` is compared with `check` and the `PUBLIC_STAGES` of its module, because its unknown-stage error has a general code. A made-up action of `change` must be refused with `UNKNOWN_COMMAND` when no other option is given, and `verify --gate` with a made-up gate with `UNKNOWN_GATE`: the dispatcher refuses them before the handler reads an option. A stray word after each of the ten commands that take no action (`next` and `decide` included) must be refused with `UNKNOWN_ARGUMENT`, and a call of `next` and of `decide` with every documented flag must not be. Broken inputs: a table row with no entry, an entry that the table does not give, and a listed action whose handler answers `UNKNOWN_COMMAND` (`component frobnicate`). Running every command for real is still the CLI's own tests' job.
- **(c) `next` (`checkNext`).** For each deliverable, tier (quick, standard, full) and mode (`brief`, `replicate`), take the action of every stage, on an empty and a full project: `stage.action(state, root)` for a deliverable that has a stage module, and for `ui` the text that `next` returns at each stage of the walk of fact 4. Take `nextAction` on an empty project for the start action. Every `designer-pipeline` command literal must be an `active`, `public` command entry whose `stages` hold `deliverable:stage`; every guide path must be an `active` guide entry; the start action must name `next` (`NEXT_NAMES`). The test also asserts that the stage list of standard tier and replicate mode contains every stage of every tier and mode, in order, that `freeform` gives the lists of `brief`, and that every deliverable in `DELIVERABLES` is covered by a stage module or by the `ui` walk, because the map and check (d) rely on it. Broken inputs: an action that names `film verify`, one that names an `expert` command, one that names a guide with no entry, a `ui` action that names a command whose entry lacks the pair `ui:<stage>`, and a walk whose `next` returns a stage it cannot finish (`walkStages` throws an error that names the deliverable and the stage).
- **(d) Public entries are named (`checkNext` and `checkSkillFiles`).** For each `deliverable:stage` of a `public` command or guide entry, a `next` action at that pair names it, or the section `## <stage>` of `references/workflow-<deliverable>.md` does; the workflow guides themselves are exempt from this (`STAGE_UNPROVEN`). Every `public` guide is named by `skill/SKILL.md`, by the repo skill or by the text of a `next` action (`GUIDE_UNNAMED`). No exception is needed for the three workflow guides: `SKILL.md` names them in "Where the details are", and after T4 the repo skill does too. The script does not read the `guide` field of `next` (`nextAction` adds it, for example `references/workflow-film.md#intake`), because the stage actions it calls do not carry it, and `tests/workflow-next.test.cjs` already tests that field. Broken inputs: a stage pair that nothing names, a public guide named by no text.
- **(e) Command examples resolve (`checkLiterals`).** Scope: every `.cjs` under `skill/scripts`, `skill/SKILL.md`, the repo skill and the guide entries that are Markdown (a guide that a later change lists, such as `evals/web/README.md`, comes into this scope from then on). `commandLiterals` returns each `designer-pipeline <first> [<second>]`. `checkLiterals` checks it when `<first>` is the first word of a command entry (52 words today, the same 52 as the keys of the command table), `<second>` matches `^(--gate [a-z-]+|[a-z][a-z0-9-]*)$`, and at least one command entry has `<first>` as its first word and a second word; it must then equal a command entry (`LITERAL_UNKNOWN`). A missing second word (the line ends), a second word starting with `<` or `-`, and a first word that starts no command entry are skipped. No list of exceptions. Broken inputs: `designer-pipeline film edit auto`; the passing cases `designer-pipeline adaptation` and `the designer-pipeline skill`.
- **(f) `SKILL.md` and the repo skill (`checkSkillFiles`).** Every guide path they name (a guide path is a path under `references/` or `evals/`, with or without a leading `skill/`, ending in `.md` or `/`; the repo skill writes `skill/references/...`; a data file such as `scripts/tool-list.json` is not a guide path) is an `active` guide entry; every command they name is an `active` command entry (`SKILL_NAMES`). Each of the two files also names `references/workflow-film.md`, `references/workflow-edit.md` and `references/workflow-web.md`, the guides that `next` sends the author to. That last rule keeps the fourth of the five disagreeing places (proposal, "Why") fixed: task T4 changes the three route bullets of the repo skill from `product-film-direction.md`, `film-edit.md` and `pipeline-reference.md` to the workflow guides (`pipeline-reference.md` stays for `ui`), and a later edit that puts other guides back fails here. Broken inputs: a text that names a guide with no entry, one that names `designer-pipeline high-fidelity check`, a repo skill without `references/workflow-web.md`, a repo skill that names `skill/evals/web/README.md` with no entry.
- **(g) The map (`checkMap`).** `renderMap(list, inputs)` equals `skill/references/tool-map.md`, after turning `\r\n` into `\n` on both sides (`MAP_STALE`; the message names `node scripts/tool-list.cjs --write`). Broken input: a changed line. A second test asserts what the map must contain: no `internal` entry, `verify audio` under `film check` and not in the on-demand list of `film`, every alias in the last section, `references/film-edit.md` in the on-demand list of `edit`, `next` under "Every deliverable".

## 8. The three entry commands and the merge question

- **What the tool list is.** A list that says what exists, who is shown it and where it is taught. It never chooses a next step, so it is not an entry command. Nothing routes from it: `next` still decides from files, `route` from words, `status` and `plan` from change state, and each entry command is checked against the list.
- **The three entry commands today.** `next` and `decide` (workflow state in `.design-pipeline/state.json`, stages `intake` to `deliver`); `route` (the 11 jobs of `job-registry.json`), whose plan `toolchain` and `execution` then use; `change`, `status`, `plan`, `run` (an OpenSpec change, phases `repo-read` to `archive` and 13 control phases). The tool list does not put them into one vocabulary. It records, for each tool, the stage of the first (`next`) that names it, and cross-checks the commands of the second (`route`; check b). The words of the third stay in `pipeline-phases.json`.
- **Merging is not needed now.** No check in this change needs it, and merging changes what `next` and `route` do, which is a behaviour change with its own tests.
- **Evidence that would justify it**, any one of: (1) the checks fail twice in two releases because two entry commands disagree (for example a job's main tool is a stage of no deliverable); (2) a real run or an evaluation shows an author using `route` where `next` was right, or the opposite; (3) evaluations for `next` on `edit`, `web` and `ui` exist (today none does) and show routing failures; (4) `ui` gets real stages, so jobs can map onto stages; (5) a maintainer has to edit three lists for one change more than once.
- **Later steps this change makes cheap** (none is started): generate the help from the tool list once a flag model exists; let stage modules look up their command names once a wording test protects `next`; add `phases` or `tiers` only when an author is misled about them; split the 20 handlers into one function per action (the follow-up of section 11).

## 11. Risks and limits

- **Summaries can drift from behaviour.** Nothing checks them. Mitigation: the plain-language rule, a person's read (section 9), and the `step1` flags.
- **The per-stage check needs a list of trigger files.** A new stage that tests for a new file would show only its empty-project text until the list grows. The reverse check (a claimed stage that nothing names) still fails, so a wrong claim cannot hide.
- **The command-example check can fail on a new false alarm.** The rule was measured on 116 examples in 155 files with none today. If prose triggers it, the fix is to narrow the scope to code spans, not to add an exception list.
- **What the command table proves after T6, and what it cannot.** The table has 52 commands. 22 already list their actions in the table (42 of the 142 rows). 30 pick their action inside their own code: 10 are a command with no action (`doctor`, `status`, `plan`, `run`, `resume`, `explain-block`, `package`, `route`, `next`, `decide`) and 20 take 90 rows (86 actions and 4 `verify --gate` values). T6 lists those 90 in the table and gives the ten commands that take no action an empty list, so that `next` and `decide` refuse a stray word as the other eight do.
  - **What is proved.** (1) Every action or gate that the CLI accepts is one the table lists: the dispatcher refuses the rest before the handler runs, with `UNKNOWN_COMMAND` or `UNKNOWN_GATE`, or with `UNKNOWN_ARGUMENT` for a stray word after a command that takes no action (`next` and `decide` included). (2) The tool list, the table and the help agree row for row (`TABLE_ENTRY`, `HELP_ENTRY`). (3) Each listed action of the 20 commands is recognised by its handler, for 84 of the 90 rows (`DEAD_ACTION`); `component-first` (5 rows) is compared with its module's own list. So an invented command or action can no longer hide behind a help line and an entry that agree.
  - **What is not proved.** That an action works: only that its handler recognises it (68 of the 90 rows are named in a test file, by a text search). That `designmd sync` is recognised: it may use the network, so it is read in the code and not run. That handlers hold no dead branch: each keeps its own `if` chain, and a branch for an action the table does not list is now unreachable, not removed. That the drive test can see a wrong name in every handler: in the trial 20 of the 21 cases answered "unknown" to a made-up action, and it knows the three handlers and the `--gate` mode that read an option first (fact 15; a fourth would need its input added), but the permanent test cannot repeat that trial after T6, because the dispatcher then refuses a made-up action before any handler sees it. That is measured, not tested.
  - **What changes for a user.** Only the answer to an action or gate that is not listed: the code is the same (`UNKNOWN_COMMAND`, `UNKNOWN_GATE`) and so is the exit code (1), but the words are the dispatcher's (`unknown command: change foo`) and the refusal comes before the handler reads its options. In the prototype that is 5 of 151 cases; every listed action answers as before. And a stray word after `next` or `decide`, which used to be ignored (`next zzz` ran `next`; `decide --stage intake --answer looks good` recorded `looks` and dropped `good`), now answers `UNKNOWN_ARGUMENT` with the words that the other eight commands that take no action already use (exit 1). A call without a stray word answers exactly as before: the prototype ran ten legitimate calls with every documented flag, and the ten commands called alone, before and after with identical answers. No caller passes a stray word (fact 15). No file of `tests/` asserts the old words (searched).
  - **Follow-up, not in this change: `split-command-handlers-by-action`.** Rewrite the 20 handlers as one function per action, so that the table's `run` entries are the real dispatch and no `if` chain is left. About 705 lines in 20 functions of `cli-core.cjs`, plus the two modules that `component-first` and `adaptation` hand over to, with tests. A full list does not need it. Trigger: a handler needs per-action option rules (as the 22 table commands have with `required`), a wrong action hides behind an option check again, or a maintainer edits the same `if` chain twice for one change.
  - Whether each command runs is the CLI's own tests' job.
- **`noGuide` can become a parking place.** The map and `qa.md` show the count.
- **Two files to keep in step (the tool list and the map).** `--check` and the test make a stale map fail QA, and one command regenerates it.
- **Step 1 can change after this is written.** T0 exists for that; three rows carry a `step1` flag.
- **Windows.** The prototypes ran on Windows only. Line endings are fixed by `.gitattributes`, and the map test normalises them anyway.
