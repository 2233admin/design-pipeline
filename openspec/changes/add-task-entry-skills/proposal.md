# Start design-pipeline by task: an index skill and five entry skills

Today you can start design-pipeline only by saying "make something". This change lets you start by the job you have: make something new, take a reference apart, try a few directions or a sample, check a finished piece, or continue a job. It adds five short skills, one per job, and shrinks `skill/SKILL.md` into an index that says where to start.

**Order: nothing can start until `fix-tool-guidance-errors` and `add-web-capability-skills` (Phase A) are committed.** None was when this was written. Task T0 stops and reports, and the user decides. Waiting costs time; going first costs either a reshaped `skill/SKILL.md` between the two packaged commits that `add-web-capability-skills` compares (it says a stray commit there must be avoided or declared), or a second edit of the index later. Details: `design.md` section 1.

## Why

Today the package is one skill, `skill/SKILL.md`, and it drives one thing: the `next` loop. Its description has 405 characters, opens with a slogan, lists only ways to make things, and has no "not for" part. The other jobs already have commands and guides, but nothing lets a person start there. On 2026-09-30 and 2026-10-01 we read the code and probed the hosts (`design.md` section 2 and Appendix A). Five findings decide the shape:

1. **Each task has something real to hand over to.** Taking a reference apart: the `reference` stage guides, `composition capture`, `film-edit analyze`. Trying directions or a sample: the quick tier, the `concepts` and `style` stages, `direction-preview.md`, `playground.md`. Checking a finished piece: `film check`, `film-edit check`, `verify interaction`, `verify composition`, `verify audio`. Continuing: `next`, which only reads and gives the same answer twice. Some limits are real too: nothing lets an agent watch or measure a reference video for film; a `ui` job cannot finish in `next` without delivery (`design.md` section 4.1).
2. **Two commands look like resume commands and are not.** `status` and `resume` work on an OpenSpec change folder only. Pointed at a `next` project they answer `UNKNOWN_SCHEMA`, and `resume` writes.
3. **Hosts list skills differently.** omp reads one folder level (its harness document, `omp://skills.md`, says nested patterns are not discovered; read). Claude Code is reported to do the same; its docs are silent and I could not run it. Codex lists nested files, does not merge two skills of one name, and skips folders that start with a dot (probed). On a machine with many skills a host cuts descriptions short: Claude Code drops the text of the least-used skills first, and Codex shows only the first 44 to 106 characters. This machine has 196 and 147 skills. Nothing in the plan depends on the Claude Code side, because the entries are installed as siblings.
4. **No current test forbids a second `SKILL.md`.** `add-web-capability-skills` plans one that says "exactly `skill/SKILL.md`". One test reads `skill/SKILL.md` directly, and eight read the main skill and its guides through one helper; none of them depends on the text that moves out.
5. **Score and 3D are not media of their own.** A score needs a storyboard and a 3D shot renders inside a film project, so there is no music-only or 3D-only job to start.

## What changes

1. **Five entry skills**, one per user task, named `dp-create`, `dp-reference`, `dp-preview`, `dp-review` and `dp-resume` (draft names, confirmed only after the host run, D17), in `skill/.entries/<name>/SKILL.md`. The folder starts with a dot so that Codex does not list the packaged copies a second time. Each entry is short: a sentence that tells the agent where the `design-pipeline` folder is, "Ask once", a table that names existing commands and guide sections, "Before you say done", and "Do not" with a reason for each item. `dp-create` is longer because the loop moves into it. None holds a rule, a keyword list or a command that runs `route`.
2. **`skill/SKILL.md` becomes an index.** It keeps the name `design-pipeline`, `## Where the details are` and `## Always`; it loses the loop, the first-call tables and "Talking to the user" (they move to `dp-create`); it gets a table of the five entries and a fallback sentence for hosts that do not list them. A scratch draft measures 47 lines and 2.8 KB, from 77 lines and 4.3 KB.
3. **Six descriptions** written for hosts that show only the start: a first sentence of at most 80 characters that names the task in its first 45; for each entry one "use this whenever ... even if they never say design-pipeline" sentence; quoted trigger phrases in English and Chinese; and one "NOT for" sentence. The rule for a sentence that names two tasks is written into the words, not only into the design. No colon followed by a space, no colon at the end, no space then `#`, no angle brackets, no backticks. The six drafts total 2,748 characters, against 405 for today's single description.
4. **The installer copies each entry into its own folder** beside the main skill. `scripts/install-local.cjs` looks at `.entries` before it copies anything, stages every copy first, writes a small marker file (`.installed-by-design-pipeline.json`) into each folder it installs, and rolls back on failure (about 45 to 60 lines). It replaces an entry folder only if that marker is there: a folder of the user's with an entry's name is never overwritten, and the installer names it and stops. `scripts/package.cjs` is not edited: it already ships the hidden folder. A linked install cannot use the installer; the README says to copy or link each entry by hand.
5. **Tests, structure only.** New `tests/entry-skills.test.cjs` (files, frontmatter, characters, shape, no copied phrases, size, names, and no command that runs `route`) and `tests/entry-names.test.cjs` (command names; the tool-list link replaces it and deletes it); the planned "exactly one `SKILL.md`" check becomes a folder rule; new installer cases, marker cases among them. The front-door helper is not changed. No test reads the wording of a description.
6. **Registration and words.** Five lines in `required` of `package-resources.json`; a README section (install per host, copy or link by hand, uninstall); one paragraph in `CONTRIBUTING.md`; three small edits in the repo router; a changelog entry.
7. **A link to the tool list**, after `add-capability-registry` lands (slice T5): its `SKILL_NAMES` check also reads the commands named in the entry files, and the generated map gets a `## Ways to start` section computed from them. No new field.

## Decisions taken

By the author, reversible, each with its reason in `design.md` section 3: five entries and the index, six listed skills, cap six entries (D1); sibling skills, with the task table kept in the index as the fallback (D2); hidden entry folder (D3); installer fan-out and no `package.cjs` edit (D4); entries hold no rules and never run `route` (D5); the medium is asked at most once per entry and never when project state holds it (D6); the index keeps its name and its reference list (D7); the description rules (D8); structure-only tests, a closing read of what no test can check, and a person's host run (D9); an allow-list and no helper change (D10); the repo router keeps its name (D11); no new tool-list field (D12); `dp-review` never calls `decide` on its own and reports tool results and human decisions apart (D13); `dp-resume` reads first and writes nothing unless told (D14); this change lands after the two drafts named above, behind a stop check (D15); an install marker in every installed folder, an entry folder replaced only when it carries the marker, and no `--no-entries` flag (D16); plain entry names, confirmed only after the host run (D17).

## Order of work

This change lands after `fix-tool-guidance-errors` and `add-web-capability-skills`. It may land before or after `add-capability-registry` (slice T5 waits for it), `align-workflow-lifecycle` and `add-web-composition-checks`: whoever lands second moves the lines it changed to the file that holds them then. ## Not in scope

- A new gate, finding code, receipt, schema, workflow stage, state field, `designer-pipeline` command or entry command. `next`, `route` and the change commands stay as they are.
- A sixth entry (`dp-clone`, `dp-fix`, `dp-score`, `dp-3d`), a music-only or 3D-only job, renaming the repo router. The entry names are draft names until the host run (D17).
- A generator for direction previews or playgrounds, a way to measure a reference video, a content check of `reference.md`, a `ui` reference stage (the lifecycle draft adds one).
- An uninstall command, removal of an entry a later release drops (the marker would allow it), `--no-entries`, and an entries-only installer mode for linked installs.
- Six follow-ups from the skill-creator audit (trigger files, optional description runs, a table of look-alike skills, the first host row, the limits of `quick_validate.py`, what `openspec validate` proves) are named in `tasks.md`. None is done here.
- Edits to the five other draft changes or their documents, and to the bmad-managed block of `AGENTS.md`.
- Running a model to see which entry a host loads: it is left to a person (T7).

## What this change does not claim

It does not say the entries load on the right sentence: no entry file exists, and no model, script or host was asked which skill it loads. **No real trigger run of any kind was done.** It does not say a host with many skills will show these descriptions. It does not say the hidden-folder choice holds beyond Codex 0.155.0. One probe result differs from a sibling draft: Codex here listed a colon followed by a space and a 1,025-character description; only a description that ended with a colon was dropped (`design.md` F4). The installer copy, with the marker, was run as a throwaway with a fake health check, not against the real package. `node scripts/qa.cjs` was not run, and `openspec validate --strict` only checks the format of the spec. Visual Acceptance does not apply: nothing here is a page or a film.
