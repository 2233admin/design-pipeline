# Acceptance design

## Fixture topology

The fixture is generated by `fixture/create.cjs` and exercised by `fixture/run.cjs` under an isolated
temporary root. It contains reusable `DESIGN.md` and `MOTION.md` foundations, one direction-preview
change, four single-file HTML Playgrounds, component request/route artifacts, and an external project
skill whose three independent promotion candidates cover communication-density, representation, and
evidence-order.

## Evaluation protocol

The evaluation manifest fixes the task list and partitions before either arm runs. Construction,
replay, and held-out fixture IDs are disjoint. The evaluator label is independent from the proposer.
Baseline and adapted rows report correction-count and preference scores as effect sizes only; they are
synthetic acceptance evidence, not a population estimate.

## Safety and recovery protocol

The runner covers state/receipt/candidate tamper, path escape and symlink boundaries, scope leakage,
live/dead lock behavior, interrupted prepared transactions, successor-chain rollback/forget, and a
two-process stress run. The lock regression is also deterministic in `tests/adaptation.test.cjs` by
injecting a lock replacement during quarantine.

## Human-readability protocol

The recorded CLI outputs are checked for candidate rule values, evidence hashes, scope, blocked exit
status/reason, effective rules, rollback target, and forget/tombstone consequences. Playground
selection prompts are written back into the next design task so the feedback loop is inspectable.

## Resource budget

Record command latency, ledger byte size, and the final 20-task ledger/CLI maintenance snapshot. A
larger ledger is not counted as adaptation unless the correction effect and invariants are both
reported.
