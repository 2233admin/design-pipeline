## Why

#19 allows custom design-system choices without evidence and downstream web/UI work does not consume the decision. #66 starts questioning before a bounded look at supplied frontend inputs, and generic UI asks film questions. This can approve the wrong purpose or silently turn a catalog miss into permission to change a project's system.

The owner authorized this repair and explicitly retained a fast, from-scratch path with no mandatory catalog search. The old #19 wording requiring every custom choice to search is not the accepted behavior.

## What Changes

- Extend the existing v1 workflow state to retain the supplied frontend request, bounded source/link scope and resolved optimize-existing, reference-for-existing or faithful-reproduction purpose.
- Return a bounded read-only observation before unresolved direction-changing questions or source modifications. Observations do not grant design acceptance.
- Use frontend questions for UI; preserve film/edit stages and capabilities.
- Validate the existing v1 design-system decision before frontend directions/spec/tasks/implementation. Explicit owner scratch records the actual selection without searching. A fallback/substitution requires a capability inventory, comparisons/rejections, compatibility, rationale and recorded owner selection. Ambiguous library identity needs clarification.
- Bind the decision and its source evidence to the existing snapshots, input hashes, policy and receipt lineage. Edits/removal reopen dependent approvals and technical evidence. Reference-only choices cannot authorize runtime adoption.
- Explain all three starts in plain language and keep quick/standard/full and existing owner decision points.
